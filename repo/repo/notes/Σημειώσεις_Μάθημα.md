# Σημειώσεις Μαθήματος: Νήματα, Διεργασίες, Παράλληλος Υπολογισμός

---

## 1. Ορίσματα Γραμμής Εντολών (Command Line Arguments)

Όταν θέλουμε να τρέξουμε ένα πρόγραμμα με διαφορετικές παραμέτρους κάθε φορά (π.χ. αριθμό νημάτων, μέγεθος δεδομένων), αντί για interactive interface χρησιμοποιούμε **command line arguments**.

- Στο `main(String[] args)`, το `args` είναι πίνακας από strings.
- Κάθε τιμή που δίνουμε στη γραμμή εντολών μετά το όνομα του προγράμματος γίνεται ένα στοιχείο: `args[0]`, `args[1]`, κ.λπ.
- Πρέπει να κάνουμε **parse** (π.χ. `Integer.parseInt(args[0])`) για να μετατρέψουμε το string σε αριθμό.

**Συνηθισμένο πρόβλημα σε IDEs (π.χ. Eclipse/VS Code):** Αν πατήσεις απλά "Run", το πρόγραμμα περιμένει ορίσματα που δεν του δόθηκαν και κολλάει/σκάει.
**Λύσεις:**
1. Στο Eclipse: **Run → Run As → Run Configurations → Arguments tab**, εκεί δίνεις τα ορίσματα.
2. Εναλλακτικά: σχολιάζεις (comment out) το κομμάτι που διαβάζει τα `args` και δουλεύεις με σταθερές τιμές ή `Scanner`/`System.in`.

## 2. Πότε σταματάει (τερματίζει προσωρινά) ένα νήμα;

Ένα νήμα "φεύγει" από την εκτέλεση (γίνεται preempted) σε μία από αυτές τις περιπτώσεις:

| Αιτία | Επεξήγηση |
|---|---|
| **Χρονοδιακοπή (time slice)** | Πέρασε ο χρόνος που του αναλογούσε· ο scheduler το διακόπτει για να δώσει CPU σε άλλο νήμα |
| **Διακοπή / Interrupt** | Λαμβάνει ένα "σήμα" (event) — βλ. ενότητα 3 παρακάτω |
| **Priority** | Αγνοήστε το — πολύ ακραία/σπάνια περίπτωση, δεν το χρησιμοποιούμε |
| **yield()** | Το νήμα οικειοθελώς παραχωρεί τη θέση του — σπάνια χρήση |
| **Thread.stop()** | Βίαιος/απότομος τερματισμός — **αποφεύγεται**, γιατί δεν κάνει σωστό garbage collection, δεν κλείνει καθαρά τα νήματα |

Στο μάθημα ασχολούμαστε κυρίως με το **interrupt**.

## 3. Interrupt (Διακοπή/Σήμα)

### Τι είναι
- Ένα **interrupt δεν είναι "σκότωμα"** με τη βίαιη έννοια — είναι ένα **σήμα (event)** που στέλνεται στο νήμα.
- Το νήμα **δεν είναι υποχρεωμένο** να τερματίσει· απλά ενημερώνεται ότι κάτι συνέβη, και ο δικός του **interrupt handler** αποφασίζει τι θα κάνει (συνήθως τερματίζει, αλλά θα μπορούσε να κάνει και κάτι άλλο, π.χ. να αποθηκεύσει κατάσταση).
- Δύο τρόποι/στιγμές που μπορεί να "χτυπήσει" το interrupt σε ένα νήμα:
  - **Κατά την εκτέλεση κώδικα** (σπάνιο αν ο κώδικας είναι μικρός)
  - **Κατά τον "ύπνο"** (π.χ. ενώ κάνει `sleep()`, `join()`, `wait()`)
- Και στις δύο περιπτώσεις, επειδή η αναστολή είναι τυλιγμένη σε `try/catch(InterruptedException)`, το νήμα **ξυπνάει** και εκτελεί τη ρουτίνα διαχείρισης διακοπής (interrupt handler) — π.χ. ένα `break` που βγάζει το νήμα από ένα `while(true)`.

### Παράδειγμα (HelloEvents)
1. Δημιουργούνται πολλά νήματα, κάθε ένα τυπώνει μήνυμα και μπαίνει σε `while(true)` περιμένοντας.
2. Το main επιλέγει ένα νήμα `i` και καλεί `threads[i].interrupt()`.
3. Το νήμα `i` "ξυπνάει" απ' όπου ήταν (εκτέλεση ή ύπνο), μπαίνει στο `catch(InterruptedException)`, κάνει `break`, και τερματίζει κανονικά.

### `interrupt()` vs `join()` — Σημαντική διάκριση
| | Τι κάνει |
|---|---|
| **`join()`** | Ο καλών **περιμένει** να τερματίσει κανονικά το νήμα |
| **`interrupt()`** | Ο καλών **στέλνει σήμα** στο νήμα να τερματίσει (event, όχι αναμονή) |

**Δεν αναιρεί το ένα το άλλο** — μπορούν να συνδυαστούν: πρώτα στέλνω `interrupt()` (σήμα διακοπής), μετά καλώ `join()` (περιμένω να επιβεβαιωθεί ότι πράγματι σταμάτησε).

### Επαναφορά (restart) μετά από interrupt
- Αν ένα νήμα **τερματίσει κανονικά** (φυσικό exit), **δεν μπορεί να ξανα-ξεκινήσει** — θα πετάξει σφάλμα, γιατί το λειτουργικό σύστημα έχει ήδη καταστρέψει τις δομές του.
- Αν το νήμα σταματήσει λόγω **interrupt** (χωρίς να βγει εντελώς από το `run()`), πιθανώς μπορεί να "ξαναρχίσει" — αλλά αυτό χρειάζεται συγκεκριμένο χειρισμό (όχι μέσα σε loop, αλλά στοχευμένα ανά αριθμό νήματος). Ο καθηγητής δεν ήταν 100% σίγουρος — το άφησε ανοιχτό για δοκιμή.

## 4. Άλλες χρήσιμες μέθοδοι της κλάσης Thread

- **`Thread.currentThread()`** — αναφορά στο τρέχον νήμα
- **Κατάσταση νήματος**: `RUNNABLE`, `READY`, `BLOCKED`, κ.λπ.
- **`isAlive()`** — αν το νήμα δεν έχει τερματίσει ακόμα
- **`setDaemon(true/false)`** — δηλώνει νήμα ως "δαίμονα" (βοηθητικό)
  - Δεν κρατάει τη JVM ανοιχτή· αν κλείσουν όλα τα κανονικά (non-daemon) νήματα, η JVM κλείνει ανεξάρτητα από το αν ο δαίμονας τρέχει ακόμα. **Δεν θα τα χρησιμοποιήσουμε** στο μάθημα, απλά καλό να ξέρεις τι σημαίνει αν το δεις.
- **`getName()` / `setName()`** — όνομα νήματος

### Συνοπτικά — τι είναι ένα Thread
- Είναι **αντικείμενο**, αλλά ιδιαίτερο: έχει δυνατότητα **ανεξάρτητης εκτέλεσης κώδικα**.
- Εκτελείται μέσω της JVM/RAM ξεχωριστά.
- Έχει δική του κατάσταση, δικούς καταχωρητές (registers), δική του στοίβα εκτέλεσης (stack).

### Java και threads
- Η Java ήταν από τις πρώτες γλώσσες που έβαλε τα νήματα **στο κέντρο της γλώσσας** (native) — δεν χρειάζεται import βιβλιοθήκης για βασική χρήση.
- Επιπλέον διαθέσιμα: `java.util.concurrent` (πολλά έτοιμα εργαλεία), `java.util.stream` (functional/παράλληλος προγραμματισμός, πιο high-level — δεν θα το καλύψουμε φέτος).
- Σε άλλες γλώσσες: C → pthreads (include), Python → threading/multiprocessing (import).

## 5. Διεργασίες (Processes) vs Νήματα (Threads)

| | Διεργασία (Process) | Νήμα (Thread) |
|---|---|---|
| Τι είναι | Ολόκληρο, ανεξάρτητο πρόγραμμα που εκτελείται | Κομμάτι εκτέλεσης **μέσα** σε μια διεργασία |
| Αυτονομία | Αυτόνομη οντότητα | **Δεν** μπορεί να υπάρξει χωρίς διεργασία |
| Παράδειγμα | Κάθε ανοιχτό παράθυρο/εφαρμογή στον υπολογιστή σου | Δύο tabs μέσα στον ίδιο editor (μοιράζονται μνήμη/executable) |

**Γιατί χρησιμοποιούμε threads αντί για νέες διεργασίες;**
- **Οικονομία**: μια νέα διεργασία απαιτεί φόρτωση εκτελέσιμου, νέο πίνακα μνήμης κ.λπ. — ακριβό. Τα threads μοιράζονται ήδη τον χώρο της διεργασίας.
- **Ανταπόκριση**: για να μη μπλοκάρει η εφαρμογή με το πρώτο I/O.
- **Εξυπηρέτηση πολλών χρηστών/παραθύρων ταυτόχρονα**.
- **Ταχύτητα** (με την έλευση πολυπύρηνων επεξεργαστών): μια διεργασία με πολλά threads εκτελείται πιο γρήγορα — αυτό είναι κι ο στόχος του παράλληλου υπολογισμού.

## 6. Δημιουργία Διεργασιών

Τρεις τρόποι:
1. **Από γραφική διεπαφή** (διπλό κλικ σε εφαρμογή)
2. **Από γραμμή εντολών** (π.χ. `java MyClass` στο terminal)
3. **Μέσα από πρόγραμμα**, με την κλάση **`ProcessBuilder`** της Java — μια Java εφαρμογή ξεκινάει άλλα προγράμματα.

### ProcessBuilder — βασικά σημεία
- Παίρνει εντολή + ορίσματα και ξεκινάει νέα διεργασία.
- **`waitFor()`** ≈ σαν το `join()` για threads: κάνει τον καλούντα να περιμένει να τελειώσει η νέα διεργασία. Χωρίς αυτό, τρέχουν παράλληλα.
- Μπορεί να δοθεί **I/O** (πληκτρολόγιο/οθόνη) στη νέα διεργασία, ώστε να μπορεί να γίνει interactive αντί για background/batch.
- **Πολλαπλές διεργασίες**: αν βάλεις `start()` (χωρίς wait) σε ξεχωριστό loop και μετά όλα τα `waitFor()` σε άλλο loop → τρέχουν **παράλληλα**, ίδια λογική με τα threads (start σε ένα loop, join σε άλλο).
- Μια διεργασία που ξεκινάς μπορεί η ίδια να είναι πολυνηματική — δεν την νοιάζει τον ProcessBuilder, βλέπει απλά "μία διεργασία".
- **Χρήσιμη εφαρμογή**: αυτοματοποίηση πειραμάτων — τρέχεις την ίδια εφαρμογή διαδοχικά με διαφορετικά ορίσματα κάθε φορά (π.χ. 1, 2, 3 threads) χωρίς να το κάνεις χειροκίνητα.
- **Ιδέα**: πολυνηματική εφαρμογή όπου κάθε νήμα, μέσα στο `run()`, ξεκινάει τη δική του διεργασία μέσω `ProcessBuilder` → «μαμά εφαρμογή» με threads που καθένα ξεκινάει διαφορετική διεργασία.

## 7. Δρομολόγηση Νημάτων (Thread Scheduling) — Επίπεδα

Όταν έχουμε διεργασίες με νήματα, υπάρχουν **δύο επίπεδα δρομολόγησης**:
1. Της **διεργασίας** (το OS αποφασίζει πότε τρέχει/σταματάει η διεργασία)
2. Των **νημάτων** μέσα στη διεργασία

### Τρεις προσεγγίσεις δρομολόγησης νημάτων

**α) User-level threads (Green threads)** — το πιο παλιό
- Η διεργασία κάνει εσωτερική δρομολόγηση· το λειτουργικό σύστημα βλέπει μόνο τη διεργασία (black box) — **δεν γνωρίζει** τα νήματα.
- Μειονέκτημα: δεν εκμεταλλεύονται πολλαπλούς πυρήνες (μόνο 1 πυρήνας τρέχει κάθε φορά), και μια κλήση συστήματος μπλοκάρει *όλη* τη διεργασία.
- Πλεονέκτημα: φορητό, φθηνό.
- Σημειογραφία: **N προς 1** (N νήματα, 1 βλέπει ο πυρήνας)

**β) Kernel-level threads** — το πιο σύγχρονο/συνηθισμένο (Java, οι περισσότερες γλώσσες)
- Όλη η πληροφορία για τα νήματα είναι γνωστή στο **λειτουργικό σύστημα** (πυρήνα). Ο πυρήνας κάνει δρομολόγηση και διεργασιών και νημάτων.
- Σημειογραφία: **N προς N**
- ⚠️ **Προσοχή στην ορολογία**: "νήματα επιπέδου πυρήνα" (kernel-level threads) **≠** "νήματα του πυρήνα" (kernel threads). Τα πρώτα είναι απλά **γνωστά** στον πυρήνα (νήματα εφαρμογών). Τα δεύτερα είναι εσωτερικά νήματα **μέσα** στο ίδιο το λειτουργικό σύστημα, με περισσότερα δικαιώματα/προνόμια — άλλο θέμα, δεν μας απασχολεί.
- Βασική βιβλιοθήκη: **POSIX threads (pthreads)** — "Portable Unix". Είναι η βάση όλων: Java threads, Python threads, C++ threads όλα βασίζονται σε pthreads.

**γ) Υβριδικά νήματα (Hybrid / Virtual threads / Managed threads / Fibers)** — η πιο σύγχρονη τάση
- Δρομολογούνται πρώτα από το **runtime της γλώσσας**, και μόνο ένας μικρός αριθμός περνάει στον πυρήνα κάθε φορά.
- Σημειογραφία: **N προς M**, όπου M << N.
- **Γιατί**: σύγχρονες εφαρμογές δημιουργούν χιλιάδες/εκατομμύρια threads· περνώντας όλα στο OS θα το "γονάτιζε". Το runtime κρατάει τα περισσότερα "στην άκρη" και δίνει στον πυρήνα μόνο όσα μπορούν να τρέξουν πραγματικά (π.χ. όσους πυρήνες έχουμε).
- Παραδείγματα ανά γλώσσα: Win32 threading, Go goroutines, Java Virtual Threads (νέα βιβλιοθήκη), Python green threads/greenlets, Kotlin coroutines, Erlang processes — όλα "managed threads" στην ουσία.

### Python — ειδική περίπτωση
- Χρησιμοποιεί kernel-level threads, αλλά ο διερμηνέας επιτρέπει **μόνο ένα νήμα να εκτελείται τη φορά** (λόγω GIL — Global Interpreter Lock, όχι ονομαστικά αναφερόμενο αλλά περιγράφεται).
- `threading`: κομψός κώδικας, **όχι** πραγματική ταχύτητα/παραλληλισμό.
- `multiprocessing`: πραγματικές διεργασίες, αλλά με API παρόμοιο με threads → χρησιμοποιείται όταν θέλεις πραγματική επιτάχυνση.

## 8. Σύγχρονη vs Ασύγχρονη Κλήση (Synchronous vs Asynchronous)

- **Σύγχρονη κλήση** (αυτό που κάναμε εμείς με `join()`): ο καλών **μπλοκάρει** και περιμένει μέχρι να τελειώσει το νήμα/κλήση.
- **Ασύγχρονη κλήση** (Reactive programming): λέμε "ξεκίνα, και όταν τελειώσεις ενημέρωσέ με" (**callback**). Ο καλών **συνεχίζει** να κάνει άλλη δουλειά, και μαζεύει το αποτέλεσμα όταν έρθει.
- **Γιατί χρησιμοποιείται**: όχι για ταχύτητα, αλλά για **χαλαρότητα/ανταπόκριση** — π.χ. όταν το αποτέλεσμα εξαρτάται από δίκτυο ή φόρτο και δεν ξέρουμε πότε θα έρθει (θα περιμέναμε άσκοπα στο `join()`).
- Κλασικό παράδειγμα: κινητό τηλέφωνο — ξεκινάς μια αργή εφαρμογή στο δίκτυο, αλλά δεν παγώνει η οθόνη· μπορείς να κάνεις κάτι άλλο ενόσω περιμένεις.
- Στη δική μας δουλειά (παράλληλος υπολογισμός) **δεν** χρησιμοποιούμε reactive — θέλουμε τα πάντα να γίνονται στον ελάχιστο δυνατό χρόνο, όχι χαλαρά.

## 9. Νήματα vs Διεργασίες — πότε χρησιμοποιούμε το καθένα

- **Πολλά νήματα**: όταν είμαστε σε **μοιραζόμενη μνήμη** (ένας υπολογιστής) — εύκολο, γρήγορο.
- **Πολλές διεργασίες**: κυρίως για **ασφάλεια** (απομόνωση) ή όταν είμαστε σε **πολλά μηχανήματα** — γιατί ένα νήμα δεν μπορεί να "ταξιδέψει" σε άλλον υπολογιστή, μόνο ολόκληρη διεργασία μεταφέρεται (κατανεμημένα συστήματα).

### Φυσική μνήμη vs Χώρος Διευθύνσεων
- **Φυσική μνήμη (RAM)**: το πραγματικό υλικό.
- **Χώρος διευθύνσεων (address space)**: η "αντίληψη" που έχει μια διεργασία για τη μνήμη της — συνήθως αντιστοιχεί σε μία μνήμη, δύσκολα εκτείνεται σε πολλές.
- Νήματα → πάντα σε μία μνήμη.
- Πολλές διεργασίες → μπορούν να συνυπάρχουν στην ίδια μνήμη ή να είναι η καθεμιά σε διαφορετική (ανεξάρτητες οντότητες).

### Πώς επικοινωνούν διεργασίες/νήματα — Δύο τρόποι
1. **Μοιραζόμενες μεταβλητές (Shared variables)**: κοινές διευθύνσεις μνήμης γνωστές σε πολλά νήματα/διεργασίες — απαιτεί κοινή φυσική μνήμη.
2. **Μεταβίβαση μηνυμάτων (Message passing)**: καμία κοινή μνήμη· απλά γνωρίζει το ένα το άλλο και στέλνει/λαμβάνει μηνύματα (π.χ. μέσω δικτύου). Λειτουργεί είτε σε μία μνήμη είτε σε πολλές (πιο ευέλικτο).

### Πίνακας 2×2 (σύστημα μνήμης × τρόπος επικοινωνίας)

| | Μοιραζόμενη Μνήμη | Κατανεμημένη Μνήμη |
|---|---|---|
| **Μοιραζόμενες μεταβλητές** | ✅ Το πιο συνηθισμένο — αυτό θα κάνουμε κυρίως | Δύσκολο, ασυνήθιστο (χρειάζεται πολλή τεχνική υποστήριξη) |
| **Μεταβίβαση μηνυμάτων** | Γίνεται, λιγότερο συνηθισμένο | ✅ Φυσικός τρόπος (π.χ. δίκτυο) |

**Συμπέρασμα:** Τα νήματα (shared variables) είναι εύκολα αλλά μόνο σε μοιραζόμενη μνήμη. Η μεταβίβαση μηνυμάτων είναι πιο δύσκολη αλλά πιο ευέλικτη — δουλεύει παντού.

## 10. Εισαγωγή στον Παράλληλο Υπολογισμό

### Στόχος
Καλύτερες επιδόσεις ή μεγαλύτερο πρόβλημα λυμένο στον ίδιο χρόνο, εκμεταλλευόμενοι πολλούς επεξεργαστές/πόρους.

### Βασική διαδικασία
1. Ξεκινάμε από **ακολουθιακό αλγόριθμο** που ήδη λύνει το πρόβλημα.
2. Το σπάμε σε κομμάτια, εισάγοντας πολλαπλές ροές ελέγχου (threads).
3. Επειδή το κάνουμε εμείς οι ίδιοι με πλήρη έλεγχο, **δεν** φοβόμαστε μη-ντετερμινισμό λόγω εξωτερικών events/interrupts (σε αντίθεση με τον ταυτόχρονο υπολογισμό — concurrency — όπου υπάρχουν).
4. Επικοινωνία κυρίως μέσω μοιραζόμενων μεταβλητών, χρειάζεται σωστή χρήση μηχανισμών συγχρονισμού.

**Παράλληλος vs Κατανεμημένος υπολογισμός — πότε το ένα, πότε το άλλο:**
- **Παράλληλος**: το κάνεις **από ανάγκη** — εξαντλείς τους πόρους ενός μηχανήματος (π.χ. πολλαπλασιασμός πινάκων 3000×3000 "κουράζει" έναν υπολογιστή).
- **Κατανεμημένος**: το κάνεις γιατί η φύση του προβλήματος είναι **απομακρυσμένη** (π.χ. client-server) — δεν έχεις επιλογή, ο server είναι μακριά.
- Στην πράξη συχνά **συνδυάζονται**: πολλοί υπολογιστές (κατανεμημένο), και κάθε υπολογιστής κάνει παράλληλο υπολογισμό εσωτερικά (π.χ. μηχανές αναζήτησης όπως Google — 50.000 υπολογιστές, ο καθένας με δικά του δεδομένα, παράλληλα βρίσκουν αποτελέσματα, μετά συλλέγονται/συνδυάζονται — προσομοίωση MapReduce).

### Ιστορική αναδρομή (Flynn's Taxonomy, 1964)
- **Καθηγητής Φλιν (Stanford)**: πώς σπάμε υπολογισμό;
- **SIMD (Single Instruction, Multiple Data)**: η ίδια εντολή εκτελείται ταυτόχρονα σε διαφορετικά δεδομένα σε διαφορετικούς επεξεργαστές (σαν ορχήστρα βιολιών που παίζουν το ίδιο κομμάτι). Χρησιμοποιείται σε ειδικό hardware (π.χ. εικόνες, πίνακες). Υπάρχει ήδη μέσα σε κάθε CPU σήμερα (auto-vectorization σε for loops).
- Εναλλακτικά: **πολλοί επεξεργαστές, κάθε ένας εκτελεί τη δική του εντολή σε διαφορετικά δεδομένα** — αυτό κάνουμε εμείς.

## 11. Συστήματα Μνήμης για Παράλληλο Υπολογισμό

### Μοιραζόμενη Μνήμη (Shared Memory)
- Ένας υπολογιστής, πολλοί πυρήνες, **μία κοινή μνήμη**.
- Κάθε επεξεργαστής τρέχει ένα νήμα.
- **Πλεονέκτημα**: Προγραμματιστικά εύκολο, κοντά στον φυσικό τρόπο σκέψης.
- **Μειονέκτημα**: Δύσκολο να **επεκταθεί** — χρειάζεται νέο hardware, δεν προσθέτεις εύκολα.
- **Αυτό κάνουμε κυρίως στο μάθημα**.

### Κατανεμημένη Μνήμη (Distributed Memory)
- Πολλοί πλήρεις υπολογιστές συνδεδεμένοι με δίκτυο, ο καθένας με **δική του μνήμη**.
- Επικοινωνία μέσω **μηνυμάτων** (π.χ. "στείλε μου την εικόνα").
- **~85% των υπολογιστικών συστημάτων** στον κόσμο είναι αυτής της μορφής (data centers, cloud, μηχανές αναζήτησης, κοινωνικά δίκτυα).
- **Πλεονέκτημα**: Εύκολα επεκτάσιμο — προσθέτεις όσα μηχανήματα θέλεις.
- **Μειονέκτημα**: Δυσκολότερος προγραμματισμός.

### GPU Computing (τρίτος τύπος — αναφέρεται, δεν διδάσκεται σε βάθος)
- GPU: πολλές, απλές ALUs, λιγότερη μνήμη, λιγότερος έλεγχος (control) — κάνει **πολλές αλλά απλές/επαναλαμβανόμενες** πράξεις, χωρίς πολλά ifs/διακλαδώσεις.
- CPU: λίγες, πολύπλοκες ALUs — κάνει **λιγότερες αλλά σύνθετες** πράξεις.
- Ιδανικό για: εικόνες, νευρωνικά δίκτυα, for loops με απλή, ομοιόμορφη δουλειά.
- Θα καλυφθεί σε μάθημα επιλογής (Υπολογισμός Υψηλών Επιδόσεων) — εδώ μόνο αναφέρεται.

## 12. Data Parallelism vs Task Parallelism

| | Data Parallelism (Παραλληλισμός Δεδομένων) | Task Parallelism (Παραλληλισμός Εργασιών) |
|---|---|---|
| Τι κοιτάει | Τις **δομές δεδομένων** του προβλήματος (πίνακες, λίστες) και τις κόβει σε κομμάτια | Τη **δομή του προγράμματος** (ρουτίνες, κλήσεις) — κάθε ρουτίνα → ένα νήμα |
| Δυσκολία | Πιο ειδικός αλλά **απλούστερος**, γρήγορες επιταχύνσεις | Πιο **γενικός** αλλά δυσκολότερος, λιγότερο αποδοτικός |
| Στο μάθημα | ✅ **Αυτό θα κάνουμε κυρίως** | Δεν θα ασχοληθούμε |

Θα δουλέψουμε κυρίως με **for loops** πάνω σε πινακοποιημένες δομές δεδομένων (και βάσεις δεδομένων αργότερα).

## 13. Το Θεμελιώδες Παράδειγμα: MAP

**MAP** = εφαρμογή μιας συνάρτησης `f` σε **κάθε στοιχείο** μιας δομής δεδομένων (πίνακας, λίστα) ξεχωριστά.

**Ακολουθιακή εκδοχή** (σκελετός):
```java
// αρχικοποίηση N στοιχείων
for (int i = 0; i < N; i++) {
    a[i] = f(a[i]);   // π.χ. τετραγωνική ρίζα
}
```

**Σημαντικό**: όταν χρονομετράμε, το `a` αρχικοποίηση/print **δεν** μπαίνει στη χρονομέτρηση — μετράμε μόνο τον "βαρύ" υπολογισμό (το for loop).

**Δύο τρόποι δεδομένων:**
- Ετοιμα δεδομένα (πίνακας)
- **Γεννήτρια δεδομένων** — π.χ. brute-force παραγωγή όλων των συνδυασμών password· δεν έχουμε τα δεδομένα εκ των προτέρων, τα παράγουμε on-the-fly.

Και στις δύο περιπτώσεις, ο στόχος είναι να κάνουμε το **for loop → parallel for**.

### Τι σημαίνει "parallel for" (εξαρτάται από περιβάλλον)
- Κάποιες γλώσσες/βιβλιοθήκες το έχουν έτοιμο (π.χ. MATLAB `parfor`, OpenMP).
- Στις περισσότερες γλώσσες (Java συμπεριλαμβανομένης) **το γράφουμε εμείς** χειροκίνητα.

## 14. Naive Parallel For — Πρόβλημα με Πάρα Πολλά Νήματα

**Η ακραία (λάθος) προσέγγιση**: ένα νήμα ανά στοιχείο.

```java
Thread[] threads = new Thread[size];  // size = μέγεθος πίνακα!
for (int i = 0; i < size; i++) {
    threads[i] = new MyThread(a, i);   // περνάμε τον πίνακα A (shared) και το i
    threads[i].start();
}
for (int i = 0; i < size; i++) threads[i].join();
```

**Γιατί είναι πρόβλημα:**
- Αν το size είναι π.χ. 100.000, φτιάχνουμε **100.000 νήματα**.
- Κάθε νήμα κοστίζει: το OS/runtime πρέπει να φτιάξει πλαίσιο εκτέλεσης (context), στοίβα (stack), να το δρομολογήσει.
- Πιθανότατα δεν έχουμε τόσους πυρήνες — πολλά νήματα θα περιμένουν άλλα να τελειώσουν.
- **Πολύ overhead** — "πληρώνουμε μεγάλη ποινή" σε σχέση με το πραγματικό όφελος.

**Σημαντικό:** Το `A` (πίνακας) είναι **μοιραζόμενη μεταβλητή** — γνωστή/προσβάσιμη από όλα τα νήματα. Το κάθε νήμα τροποποιεί μόνο το δικό του στοιχείο.

## 15. Ομαδοποίηση (Grouping) — Η Σωστή Προσέγγιση

**Ιδέα**: αντί για ένα νήμα ανά στοιχείο, δίνουμε σε κάθε νήμα μια **ομάδα/φέτα** στοιχείων.

- Ισορροπία ανάμεσα σε: **πλήρως ακολουθιακή εκτέλεση** (1 "νήμα" = όλα) και **πλήρως παράλληλη** (1 νήμα ανά στοιχείο).
- Το μέγεθος της ομάδας εξαρτάται από το **βάρος (κόστος) του υπολογισμού**:
  - Βαρύς υπολογισμός → λίγα στοιχεία ανά ομάδα αρκούν (π.χ. 5, 10, 100).
  - Ελαφρύς υπολογισμός → χρειάζονται πολλά στοιχεία ανά ομάδα για να "αξίζει" η δημιουργία νήματος.

### Μαθηματικός τύπος για το βέλτιστο μέγεθος ομάδας (G)

Μεταβλητές:
- `N` = μέγεθος προβλήματος (πλήθος στοιχείων)
- `G` = μέγεθος κάθε ομάδας
- `N/G` = πλήθος ομάδων (άρα και νημάτων)
- `C` = κόστος δημιουργίας/διαχείρισης ενός νήματος (overhead)
- `T` = χρόνος εκτέλεσης μιας μονάδας υπολογισμού

Συνολικός χρόνος = (πλήθος ομάδων) × (κόστος διαχείρισης + χρόνος εκτέλεσης ομάδας)

Ελαχιστοποιώντας ως προς `G`, βρίσκουμε το βέλτιστο `G`. **Δεν υπάρχει μία univerισμαλ απάντηση** — εξαρτάται από:
- Πόσους επεξεργαστές έχουμε
- Πόσο κοστίζει η δημιουργία νήματος στο συγκεκριμένο μηχάνημα/περιβάλλον
- Το `N` και το `T` του συγκεκριμένου προβλήματος

**Βασικός κανόνας:** Θέλουμε ο **χρόνος διαχείρισης** (overhead) να είναι **πολύ μικρός** σε σχέση με τον **χρόνο υπολογισμού** — αλλιώς σπαταλάμε όλο τον χρόνο σε "γραφειοκρατία" αντί για πραγματική δουλειά.

**Ενδεικτικά κόστη (C) ανά τεχνολογία:**
- Διεργασίες: **μεγάλο** κόστος → δύσκολο να διαχειριστούμε πολλές σε έναν υπολογιστή
- Νήματα: **μεσαίο** κόστος → μιλάμε για τάξεις μεγέθους δεκάδων-εκατοντάδων (ίσως χιλιάδων σε ισχυρό μηχάνημα)
- GPUs: **πολύ μικρό** κόστος → χιλιάδες/εκατομμύρια μικρές δουλειές χωρίς πρόβλημα

## 16. Στατική Κατανομή (Static Allocation) — Πρακτική Υλοποίηση

Ο **πιο απλός** τρόπος να κατανείμουμε εργασία σε **σταθερό, περιορισμένο αριθμό νημάτων**.

### Ιδέα
- Έχουμε `size` στοιχεία και `numThreads` νήματα (numThreads **πολύ μικρότερο** από size).
- Κόβουμε τα δεδομένα σε **ισομερείς φέτες**:
  - Νήμα 0 → στοιχεία `[0, size/numThreads)`
  - Νήμα 1 → στοιχεία `[size/numThreads, 2*size/numThreads)`
  - Νήμα i → στοιχεία `[i*block, (i+1)*block)`, όπου `block = size/numThreads`
  - **Το τελευταίο νήμα** παίρνει και το τυχόν υπόλοιπο (αν η διαίρεση δεν είναι ακριβής).

### Σκελετός κώδικα (η βασική λογική SPMD — βλ. παρακάτω)

```java
public class ParallelMap {
    public static void main(String[] args) {
        int size = ...;          // από command line
        int numThreads = ...;    // από command line
        double[] a = new double[size];
        // αρχικοποίηση a[]...

        Thread[] threads = new Thread[numThreads];
        for (int i = 0; i < numThreads; i++) {
            threads[i] = new WorkerThread(i, numThreads, size, a);
            threads[i].start();
        }
        for (int i = 0; i < numThreads; i++) {
            try { threads[i].join(); } catch (InterruptedException e) {}
        }
        // εδώ το a[] είναι έτοιμο
    }
}

class WorkerThread extends Thread {
    int myID, numThreads, size;
    double[] a;

    public WorkerThread(int myID, int numThreads, int size, double[] a) {
        this.myID = myID;
        this.numThreads = numThreads;
        this.size = size;
        this.a = a;   // ίδια αναφορά σε όλα τα threads -> shared variable
    }

    public void run() {
        int block = size / numThreads;
        int start = myID * block;
        int stop  = (myID == numThreads - 1) ? size : start + block;  
        // το τελευταίο νήμα παίρνει και το υπόλοιπο

        for (int i = start; i < stop; i++) {
            a[i] = Math.sqrt(a[i]);   // η "βαριά" δουλειά
        }
    }
}
```

**Σημείωση:** Κάθε νήμα ξέρει: ποιο είναι (`myID`), πόσα νήματα υπάρχουν συνολικά (`numThreads`), τον πίνακα (`a`, shared), και το μέγεθος (`size`) — και **μόνο του** υπολογίζει το δικό του `start`/`stop`.

## 17. SPMD — Single Program, Multiple Data

Αυτή η τεχνική (στατική κατανομή μέσα σε κάθε νήμα) λέγεται **SPMD**.

- **Το ίδιο πρόγραμμα** (`run()` κώδικας) τρέχει σε **όλα τα νήματα**, αλλά κάθε ένα δουλεύει πάνω σε **διαφορετικό κομμάτι δεδομένων** (καθορισμένο από το δικό του `start`/`stop`).
- Είναι η **πιο κλασική τεχνική παράλληλου υπολογισμού** — δουλεύει παντού: πολυπύρηνα μηχανήματα, clusters, GPUs.
- Σπάμε ένα πινακοποιημένο πρόβλημα σε κομμάτια, κάθε "worker" κάνει το κομμάτι του.
- Η δουλειά μας είναι το **tuning**: να βρούμε τον σωστό αριθμό νημάτων.
- Σε **φωλιασμένα (nested) for loops**, σπάμε συνήθως μόνο το **εξωτερικό** loop (το εσωτερικό μένει ολόκληρο μέσα σε κάθε νήμα) — υπάρχει τρόπος να σπάσουμε και το εσωτερικό, αλλά όχι ακόμα στο μάθημα.

### Πρακτικό παράδειγμα εφαρμογής SPMD: Matrix-Vector Multiplication
- Παίρνεις τον γενικό κώδικα (σκελετός main + worker thread) που έγραψες για την τετραγωνική ρίζα.
- Αντικαθιστάς μόνο: (α) την αρχικοποίηση δεδομένων (τώρα πίνακας×διάνυσμα αντί για απλός πίνακας), (β) το εσωτερικό υπολογιστικό κομμάτι μέσα στο `run()` (τώρα πολλαπλασιασμός γραμμής×διανύσματος αντί για sqrt).
- Το `start`/`stop` (στατική κατανομή) **μένει ίδιο** — ίδια λογική ανεξαρτήτως προβλήματος.
- Αν θέλεις να "βαρύνεις" τεχνητά το πρόβλημα (χωρίς να χρειάζεται τεράστια δεδομένα), μπορείς να προσθέσεις ένα "περιττό" επιπλέον for loop μέσα στον υπολογισμό.

## 18. Χρονομέτρηση και Speedup (Επιτάχυνση)

### Πώς μετράμε χρόνο εκτέλεσης στη Java
```java
long start = System.currentTimeMillis(); // ή nanoTime()
// ... ο βασικός υπολογισμός (χωρίς I/O!) ...
long end = System.currentTimeMillis();
System.out.println("Χρόνος: " + (end - start) + " ms");
```

### ⚠️ ΚΡΙΣΙΜΟΣ ΚΑΝΟΝΑΣ: Ποτέ I/O μέσα στη χρονομέτρηση!
- **Ποτέ** μην βάζεις `System.out.println` (ή οποιοδήποτε I/O) **μέσα** στο κομμάτι που χρονομετράς.
- Γιατί: το I/O εξαρτάται από το λειτουργικό σύστημα/κονσόλα, όχι από τον πραγματικό υπολογισμό σου — θα σου "χαλάσει" εντελώς τη μέτρηση (το χειρότερο δυνατό: "καταστροφή" όπως το είπε ο καθηγητής).
- Θέλουμε να μετράμε **καθαρό χρόνο υπολογισμού**.
- Αν βάλεις εκτύπωση μέσα σε διπλό for loop που χρονομετράς: **δεν κερδίζεις τίποτα** από τον παραλληλισμό — μόνο χάνεις.
- Εξαίρεση αξιοσημείωτη: αν το ίδιο το πρόγραμμα *είναι* για να κάνει πολλά I/O (π.χ. πολλές εκτυπώσεις ή αναγνώσεις), τότε το όφελος του παραλληλισμού έρχεται μόνο από το ότι το OS μπορεί να εξυπηρετήσει πολλά νήματα ταυτόχρονα (ενώ ένα περιμένει σε I/O, τρέχει άλλο) — αυτό είναι **ταυτοχρονισμός (concurrency)**, όχι πραγματική επιτάχυνση υπολογισμού.

### Speedup (Επιτάχυνση)
**Ορισμός**: Τρέχουμε το ίδιο πρόβλημα με διαφορετικό αριθμό νημάτων/επεξεργαστών και βλέπουμε πόσο βελτιώνεται ο χρόνος.

**Παράδειγμα από τη διάλεξη** (10 εκατομμύρια στοιχεία):
| Νήματα | Χρόνος (ms) |
|---|---|
| 2 | 247 |
| 4 | 135 |
| 8 | 79 |
| 16 | ~97 (χειρότερα!) |
| 32 | δεν βελτιώνεται |

**Παρατηρήσεις:**
- Από 2→4 threads: 247→135ms ≈ σχεδόν στο μισό (καλή κλιμάκωση, "διπλασιάσαμε επεξεργαστές, πετύχαμε περίπου μισό χρόνο").
- Από 4→8: ξανά περίπου στο μισό — ακόμα καλά.
- **Στα 16 threads σε μηχάνημα με 8 πυρήνες**: ο χρόνος **σταματά να βελτιώνεται** (ή και χειροτερεύει ελαφρώς) — τα 16 νήματα πρέπει να "στριμωχτούν" σε 8 πυρήνες, τα πρώτα 8 τρέχουν, μετά τα άλλα 8. Δεν έχει νόημα να βάλεις παραπάνω νήματα από πυρήνες αν ο υπολογισμός δεν αντέχει άλλο σπάσιμο.
- **Δύο ειδών περιορισμοί που πρέπει πάντα να λαμβάνουμε υπόψη:**
  1. **Hardware**: πόσους πραγματικούς πυρήνες έχει το μηχάνημά μας (hyper-threading **δεν** μετράει σαν επιπλέον πραγματικό πυρήνα για δρομολόγηση νημάτων).
  2. **Αλγόριθμος**: πόσο "βαρύς" είναι ο υπολογισμός — π.χ. πολλαπλασιασμός πινάκων 3000×3000 (O(n³)) θα "γονάτιζε" νωρίτερα από απλή τετραγωνική ρίζα (O(n)).

**Πολύ μεγάλος αριθμός νημάτων (π.χ. 256, 512, 1024, 2048+):**
- Ο χρόνος αρχίζει σιγά-σιγά να μεγαλώνει ξανά — φτάνουμε στο σημείο που το κόστος διαχείρισης νημάτων υπερισχύει του οφέλους.
- Υπάρχουν ειδικά **micro-benchmarks** που μετρούν ακριβώς αυτά τα κόστη (πόσο κοστίζει μια βιβλιοθήκη νημάτων σε συγκεκριμένο μηχάνημα).

## 19. Η Πρακτική Άσκηση (Εργασία) — Τι Ζητείται

1. **Πάρε τον έτοιμο κώδικα** (τετραγωνική ρίζα με SPMD/στατική κατανομή).
2. **Εφάρμοσε την ίδια τεχνική** στο πρόβλημα πολλαπλασιασμού πίνακα×διανύσματος (matrix-vector multiplication) — αντίγραφο του κώδικα, άλλαξε μόνο αρχικοποίηση + βασικό υπολογισμό, το start/stop μένει ίδιο.
3. **Κάνε υπολογιστική μελέτη**: δοκίμασε διαφορετικά μεγέθη προβλήματος και διαφορετικό αριθμό νημάτων, μέτρησε τους χρόνους (χωρίς I/O στη μέτρηση!).
4. **Κατέγραψε τα αποτελέσματα** σε πίνακα (γραμμές=μεγέθη προβλήματος, στήλες=αριθμός νημάτων/πυρήνων) και σχολίασε:
   - Σε ποιο μέγεθος προβλήματος κερδίζουμε αισθητά από τον παραλληλισμό.
   - Σε ποιο μέγεθος δεν κερδίζουμε τίποτα (ή και χάνουμε).
   - Γιατί συμβαίνει αυτό (πολύ ελαφρύ πρόβλημα → overhead νημάτων υπερισχύει).
5. (Προαιρετικά) Αν το πρόβλημα είναι πολύ "ελαφρύ" για να δείξει διαφορά, πρόσθεσε ένα επιπλέον (τεχνητά "περιττό") for loop μέσα στον υπολογισμό για να το κάνεις πιο βαρύ, χωρίς να χρειάζεσαι τεράστια δεδομένα.

**Βασικός στόχος της άσκησης:** να κατανοήσεις πρακτικά την ισορροπία ανάμεσα σε:
- Κόστος δημιουργίας/διαχείρισης νημάτων
- Πραγματικό υπολογιστικό όφελος
- Hardware περιορισμούς (αριθμός πυρήνων)
- Χαρακτηριστικά του συγκεκριμένου αλγορίθμου

## 20. Γρήγορη Ανακεφαλαίωση — Βασικές Έννοιες με μία Πρόταση

| Έννοια | Σε μία πρόταση |
|---|---|
| **Interrupt** | Σήμα προς νήμα ("κάτι συνέβη"), όχι βίαιος τερματισμός· ο handler αποφασίζει τι θα κάνει |
| **join() vs interrupt()** | Το join περιμένει τερματισμό· το interrupt στέλνει σήμα διακοπής — συνδυάζονται |
| **Διεργασία vs Νήμα** | Διεργασία = αυτόνομο πρόγραμμα· Νήμα = κομμάτι εκτέλεσης μέσα σε διεργασία |
| **ProcessBuilder** | Java class για να ξεκινάς άλλες διεργασίες μέσα από πρόγραμμα |
| **Kernel-level threads** | Το OS γνωρίζει τα νήματα (πιο σύγχρονο, πιο συνηθισμένο) |
| **Managed/Virtual threads** | Runtime διαχειρίζεται πολλά νήματα, περνάει λίγα στον πυρήνα κάθε φορά |
| **Sync vs Async κλήση** | Sync = περιμένω (join)· Async = "πες μου όταν τελειώσεις" (callback) |
| **SIMD** | Ίδια εντολή, διαφορετικά δεδομένα, ταυτόχρονα |
| **Data vs Task Parallelism** | Σπάμε δεδομένα (απλό, θα το κάνουμε) vs σπάμε ρουτίνες (δύσκολο) |
| **MAP** | Εφαρμογή συνάρτησης σε κάθε στοιχείο δομής δεδομένων |
| **Ομαδοποίηση (Grouping)** | Δίνουμε "φέτες" δεδομένων ανά νήμα αντί για 1 στοιχείο/νήμα |
| **Στατική κατανομή** | Κάθε νήμα υπολογίζει το δικό του start/stop με βάση το ID του |
| **SPMD** | Ίδιο πρόγραμμα, διαφορετικά δεδομένα ανά νήμα |
| **Speedup** | Πόσο βελτιώνεται ο χρόνος όταν αυξάνουμε νήματα/πυρήνες |
| **Ποτέ I/O στη χρονομέτρηση** | Χαλάει εντελώς τη μέτρηση — μετράμε καθαρό υπολογισμό |

## 21. Μεθοδολογία Πειραμάτων — Πρακτικοί Κανόνες

### Σχέση μεγεθών προβλήματος και αριθμού νημάτων
- Επιλέγουμε μεγέθη προβλήματος και αριθμούς νημάτων που έχουν **λογική σχέση μεταξύ τους** — συνήθως **δυνάμεις του 2** (1, 2, 4, 8, 16...) ή δυνάμεις άλλου αριθμού, ανάλογα με τη φύση του προβλήματος.

### Αναξιοπιστία μικρών χρόνων
- Αν το πρόβλημα είναι πολύ μικρό, οι χρόνοι μέτρησης είναι **αναξιόπιστοι** — λίγα milliseconds επηρεάζονται πολύ από το λειτουργικό σύστημα.
- Χρειαζόμαστε **αρκετά "βαριά"** προβλήματα — τουλάχιστον δεκάδες/εκατοντάδες ms, ιδανικά δευτερόλεπτα, για αξιόπιστη μέτρηση.
- Πολύ μικρές μετρήσεις (π.χ. μόλις 3-10 ms) δεν είναι αξιόπιστες· χρειάζεται να κατέβεις σε **nanoseconds** ακρίβεια και να είσαι σίγουρος ότι το σύστημα δεν τρέχει τίποτα άλλο ταυτόχρονα.

### Πρώτο πείραμα: Ένα νήμα (ακολουθιακή εκτέλεση)
- Τρέχουμε το πρόγραμμα **ακολουθιακά** (με 1 νήμα) αυξάνοντας το μέγεθος του προβλήματος.
- Αυτό μας δίνει μια **χονδρική εκτίμηση της πολυπλοκότητας** του αλγορίθμου:
  - Αν είναι **γραμμικό** (O(n)) → διπλασιάζοντας το μέγεθος, διπλασιάζεται ο χρόνος.
  - Αν είναι **τετραγωνικό** (O(n²), π.χ. 2 φωλιασμένα for loops) → τετραπλασιασμός μεγέθους → τετραπλασιασμός χρόνου... αλλά προσοχή, γενικά: 2× μέγεθος → 4× χρόνος στο O(n²).
  - 3 φωλιασμένα loops → O(n³).
- Χρήσιμο τεστ: όσοι δοκίμασαν πολλαπλασιασμό πινάκων (3 φωλιασμένα for) θα είδαν πολύ μεγαλύτερη αύξηση χρόνου σε σχέση με απλά προβλήματα.

### Δεύτερο πείραμα: Αύξηση νημάτων
- Αφού βεβαιωθούμε ότι το ακολουθιακό πρόγραμμα τρέχει ικανοποιητικά, αυξάνουμε τα νήματα (2, 4, 8...) όσο το επιτρέπει το μηχάνημα.
- Παίρνουμε διάγραμμα χρόνου vs νήματα.

### Δύο "οικογένειες" παραμέτρων που επηρεάζουν το αποτέλεσμα

**A) Σχετικές με το μηχάνημα (hardware):**
- Πόσους επεξεργαστές/πυρήνες έχουμε **πραγματικά διαθέσιμους** στο λειτουργικό σύστημα.
  - ⚠️ **Δεν** μας ενδιαφέρει τι λέει ο κατασκευαστής ή αν είναι "λογικοί" ή "φυσικοί" πυρήνες (hyper-threading) — μας ενδιαφέρει **τι βλέπει/περνάει το OS στον compiler/JVM**, δηλαδή πόσα νήματα μπορεί ουσιαστικά να τρέξει.
- Το κόστος δημιουργίας νήματος (πιο σύγχρονο/ισχυρό σύστημα → μικρότερο κόστος δημιουργίας νήματος).
- Αν συνεχίσουμε να προσθέτουμε νήματα πέρα από τον αριθμό πυρήνων που έχουμε → η απόδοση **σταθεροποιείται ή χειροτερεύει** (τα νήματα ανταγωνίζονται για CPU).

**B) Σχετικές με το πρόβλημα:**
- Πόσο "βαρύ" είναι το υπολογιστικό φορτίο μέσα σε κάθε επανάληψη/νήμα.
- **Ελαφρύ πρόβλημα** → οι καμπύλες χρόνου δείχνουν μικρές/γρήγορες μειώσεις (ή και αυξήσεις) — δεν υπάρχει αρκετό φορτίο για να "αξίζει" τον διαμοιρασμό.
- **Βαρύ πρόβλημα / μεγάλο μέγεθος** → πιο εντυπωσιακή μείωση χρόνου με την αύξηση νημάτων.

## 22. Κανόνες Σωστής Χρονομέτρησης

1. **Μετράμε χρόνο στο main**, όχι μέσα στα επιμέρους νήματα.
2. **Καμία εκτύπωση** (`System.out.println`) μέσα στο κομμάτι που χρονομετράμε — ούτε στο main, ούτε στα threads. Αν βάλουμε, ο έλεγχος περνάει στο λειτουργικό σύστημα και η μέτρηση γίνεται **αναξιόπιστη**.
3. **Καμία εισαγωγή δεδομένων (I/O input)** μέσα στη χρονομέτρηση — ίδιος λόγος.
4. Θέλουμε **καθαρό χρόνο υπολογισμού**.

## 23. Speedup (Επιτάχυνση) — Επίσημος Ορισμός

### Τι είναι, τι δεν είναι
- Το speedup **δεν** είναι μέτρο σύγκρισης ανάμεσα σε:
  - Διαφορετικούς υπολογιστές
  - Διαφορετικούς αλγορίθμους
  - Διαφορετικούς compilers
- **Είναι** μέτρο για το πόσο καλά παραλληλοποιείται ο **ίδιος αλγόριθμος στο ίδιο μηχάνημα, με τον ίδιο compiler** — δηλαδή "πόσο καλός είναι ο δικός μας αλγόριθμος στο να εκμεταλλεύεται πολλούς επεξεργαστές".

### Τύπος
```
Speedup(p) = Χρόνος με 1 νήμα / Χρόνος με p νήματα
```

### Σχετική vs Απόλυτη Επιτάχυνση
- **Απόλυτη επιτάχυνση**: θα συνέκρινε με ένα **καθαρά ακολουθιακό** πρόγραμμα (χωρίς καν δημιουργία/καταστροφή νήματος).
- **Σχετική επιτάχυνση** (αυτή που συνήθως χρησιμοποιούμε, "επειδή βαριόμαστε"): παίρνουμε το **ίδιο παράλληλο πρόγραμμα** και απλά το τρέχουμε με παράμετρο νημάτων = 1.
  - Αυτό ελαφρώς "επιβαρύνει" την ακολουθιακή εκδοχή (έχει το κόστος δημιουργίας/καταστροφής 1 νήματος), αλλά το κάνουμε για **οικονομία προσπάθειας** (δεν γράφουμε ξεχωριστό καθαρά ακολουθιακό πρόγραμμα).

### Σχήμα καμπύλης speedup
- Έχει **αντίθετη** μορφή από την καμπύλη χρόνου: όσο αυξάνονται οι επεξεργαστές, το speedup **αυξάνεται αλλά με φθίνοντα ρυθμό** — καμπύλη που **κάμπτεται** (flattens), σε αντίθεση με την **ευθεία** που θα αντιπροσώπευε **τέλεια γραμμική επιτάχυνση**.
- **Ιδανική/τέλεια γραμμική επιτάχυνση**: αν διπλασιάσεις επεξεργαστές, ο χρόνος γίνεται ακριβώς μισός· αν τετραπλασιάσεις, γίνεται ακριβώς 1/4.
- **Στην πράξη** σχεδόν ποτέ δεν πετυχαίνουμε την ιδανική τιμή — π.χ. αντί για ÷2 παίρνουμε ÷1.8, αντί για ÷4 παίρνουμε ÷3.6. Η καμπύλη **αποκλίνει** από τη γραμμική.
- **Γιατί αποκλίνει:**
  - Κόστος δημιουργίας/καταστροφής νημάτων.
  - Γενικά αλγοριθμικά προβλήματα που επηρεάζουν την απόδοση (βλ. Νόμος Amdahl παρακάτω).

## 24. Δύο Επιπλέον Μετρικές: Κόστος και Αποδοτικότητα (Efficiency)

Προκύπτουν εύκολα από το speedup — απλά βοηθούν στην καλύτερη κατανόηση.

| Μετρική | Τύπος | Επεξήγηση |
|---|---|---|
| **Κόστος ακολουθιακής εκτέλεσης** | = Χρόνος | Απλά ο χρόνος εκτέλεσης |
| **Κόστος παράλληλης εκτέλεσης** | = (αριθμός επεξεργαστών) × (παράλληλος χρόνος) | Πόσο "επεξεργαστικό χρόνο" καταναλώθηκε συνολικά |
| **Αποδοτικότητα (Efficiency)** | = Κόστος ακολουθιακής / Κόστος παράλληλης = Speedup / p | Πόσο % του "ωφέλιμου" χρόνου επεξεργαστών χρησιμοποιήσαμε |

### Ερμηνεία Efficiency
- Αν **efficiency = 100%** → η επιτάχυνση είναι πλήρης (τέλεια αξιοποίηση επεξεργαστών).
- Στην πράξη, σχεδόν πάντα **< 100%** (π.χ. 80% κ.λπ.), γιατί η επιτάχυνση δεν είναι ποτέ απόλυτα γραμμική.

### Παράδειγμα: "Σπατάλη" (Wasted work)
- Ακολουθιακός αλγόριθμος: 100 ms.
- Παράλληλος με 2 νήματα: 55 ms.
- **Κόστος παράλληλης εκτέλεσης** = 2 × 55 = **110** "μονάδες επεξεργαστικού χρόνου".
- Ακολουθιακό κόστος = 100.
- Η διαφορά **110 - 100 = 10** είναι **σπατάλη** — επιπλέον δουλειά που δεν προσέφερε τίποτα ωφέλιμο (π.χ. σχετίζεται με διανομή δεδομένων, συλλογή αποτελεσμάτων).
- Αν είχαμε πετύχει χρόνο 50 ms με 2 νήματα (κόστος = 100, ίδιο με το ακολουθιακό) → θα ήταν **βέλτιστο ως προς κόστος (cost-optimal)**: 100% efficiency.

### "Cost-optimal" αλγόριθμος
- Ένας αλγόριθμος λέγεται **cost-optimal** όταν πετυχαίνει **100% efficiency** — δεν είναι απαραίτητα ο **γρηγορότερος** σε απόλυτο χρόνο, αλλά χρησιμοποιεί **πλήρως** το διαθέσιμο υπολογιστικό δυναμικό χωρίς σπατάλη.
- Μπορεί άλλος αλγόριθμος να είναι πιο **γρήγορος** αλλά πιο **σπάταλος** (χρησιμοποιεί περισσότερους πόρους για μικρό επιπλέον κέρδος χρόνου), και άλλος να είναι ο πιο **αποδοτικός** (καλύτερη efficiency).

## 25. Μέσος Όρος Μετρήσεων — Πρακτική Οδηγία

- Επειδή οι χρόνοι διαφέρουν κάθε φορά που τρέχουμε το ίδιο πείραμα, παίρνουμε **μέσο όρο πολλών επαναλήψεων** — συνήθως **5 έως 10 τρεξίματα** ανά περίπτωση.
- **Έλεγχος αξιοπιστίας**: αν οι μεμονωμένοι χρόνοι διαφέρουν λιγότερο από περίπου **5-10%** μεταξύ τους → OK, παίρνουμε μέσο όρο με σιγουριά.
- Αν οι χρόνοι διαφέρουν **πολύ περισσότερο** → κάτι δεν πάει καλά:
  - Το μέγεθος του προβλήματος είναι πολύ μικρό (θόρυβος από OS).
  - Υπάρχει κάποιο άλλο πρόβλημα στη μέτρηση.
- **Τα αποτελέσματα είναι ποιοτικά, όχι απόλυτα ακριβή** — δεν έχει νόημα να πάμε "στο κόμμα" (π.χ. speedup = 1,73421). Λέμε πράγματα όπως *"πετύχαμε speedup περίπου 1,7"* ή *"efficiency περίπου 80%"*.

## 26. Νόμος του Amdahl (Amdahl's Law)

### Βασική ιδέα
Ο χρόνος εκτέλεσης ενός προγράμματος χωρίζεται σε δύο κομμάτια:
- **α (alpha)**: το **παραλληλοποιήσιμο** τμήμα του χρόνου εκτέλεσης
- **1 - α**: το **μη παραλληλοποιήσιμο** (καθαρά ακολουθιακό) τμήμα

Κανονικοποιούμε τον συνολικό χρόνο εκτέλεσης στη μονάδα (1), άρα:
```
Χρόνος ακολουθιακής εκτέλεσης = α + (1 - α)
```

**Σημαντικό:** το `α` και το `1-α` είναι **χρόνοι εκτέλεσης**, **όχι** ποσοστά γραμμών κώδικα.

### Ο τύπος του Amdahl
Όταν εκτελούμε παράλληλα με `p` επεξεργαστές, το παραλληλοποιήσιμο κομμάτι `α` **διαιρείται τέλεια** με το `p` (θεωρούμε ιδανικό παραλληλισμό εκεί), ενώ το `1-α` **μένει σταθερό** (δεν μπορεί να μοιραστεί):

```
Χρόνος παράλληλης εκτέλεσης = α/p + (1 - α)

Speedup(p) = 1 / [ α/p + (1 - α) ]
```

### Οριακή περίπτωση: p → ∞
Αν βάζουμε άπειρους επεξεργαστές, το `α/p → 0`, άρα:

```
Μέγιστο δυνατό Speedup = 1 / (1 - α)
```

**Συμπέρασμα-κλειδί:** Το **μη παραλληλοποιήσιμο κομμάτι (1-α)** είναι αυτό που **καθορίζει το ανώτατο όριο** της επιτάχυνσης που μπορούμε ποτέ να πετύχουμε, ανεξάρτητα από το πόσους επεξεργαστές προσθέσουμε.

### Οπτικοποίηση (διάγραμμα)
- Σκούρο κομμάτι = 1-α (ακολουθιακό, δεν αλλάζει ποτέ μέγεθος).
- Γαλάζιο κομμάτι = α (παραλληλοποιήσιμο).
- Με 2 επεξεργαστές: το γαλάζιο διαιρείται στο μισό, το σκούρο μένει ίδιο.
- Με 4: το γαλάζιο διαιρείται στο 1/4, το σκούρο ίδιο.
- Με 8, 16...: το γαλάζιο συνεχώς μικραίνει, το σκούρο **παραμένει σταθερό**.
- Τελικά το σκούρο κομμάτι **κυριαρχεί** πλήρως — γι' αυτό η καμπύλη speedup έχει **σημείο κορεσμού** (δεν αυξάνεται απεριόριστα, "ισοπεδώνεται").

### Ιστορική σημασία και αντίρρηση
- Όταν πρωτοδημοσιεύτηκε ο νόμος, δημιούργησε την εντύπωση ότι **δεν αξίζει να βάζουμε πολλούς επεξεργαστές** — γιατί ακόμα και με 95% παραλληλοποιήσιμο κώδικα (α=0.95, δηλαδή μόλις 5% ακολουθιακό), το μέγιστο speedup είναι μόνο **20×**, και αυτό επιτυγχάνεται σχετικά εύκολα ήδη με 256-512 επεξεργαστές — άρα "γιατί να βάλεις παραπάνω;"

### Δύο αντεπιχειρήματα που μετρίασαν αυτή την αρνητική εντύπωση

**1. Δεν παραλληλίζουμε όλο τον κώδικα, μόνο τα κομμάτια που το χρειάζονται**
- Το `α` στην πράξη μπορεί να είναι μικρότερο απ' ό,τι νομίζαμε — παραλληλίζουμε επιλεκτικά μόνο τα κομμάτια που αξίζει, όχι τυφλά τα πάντα.
- Πρέπει επίσης να **επιλέξουμε τον κατάλληλο αλγόριθμο** — δεν αρκεί να πάρουμε έναν τυχαίο αλγόριθμο και να περιμένουμε καλά αποτελέσματα· πρέπει να παραλληλοποιήσουμε τον αλγόριθμο **με τον καλύτερο δυνατό τρόπο**.

**2. Όσο μεγαλώνει το μέγεθος του προβλήματος, το (1-α) μικραίνει ως ποσοστό**
- Παράδειγμα: πολλαπλασιασμός πίνακα 1000×1000 έχει κάποιο 1-α. Στο 2000×2000, το 1-α είναι **μικρότερο** ως ποσοστό. Στο 3000×3000, ακόμα μικρότερο.
- Άρα **όσο μεγαλύτερο το πρόβλημα, τόσο λιγότερο μας "χτυπάει" το μη-παραλληλοποιήσιμο μέρος**.

**Επιπλέον σκέψη**: δεν είναι απαραίτητο να παραλληλοποιήσουμε *όλο* τον αλγόριθμο με την **ίδια αρχιτεκτονική** — μπορούμε να χρησιμοποιήσουμε διαφορετικές συσκευές για διαφορετικά κομμάτια (π.χ. GPU για το κομμάτι που είναι "καθαρός παραλληλισμός", άλλη συσκευή/τεχνική για πιο γενικό παραλληλισμό) — έτσι μειώνουμε την εξάρτηση από το Amdahl's law.

### Πρακτική σημασία για το μάθημά μας
- Τα προβλήματα που θα κάνουμε είναι τέτοιας φύσης που ο νόμος του Amdahl θα παίζει **μικρό ρόλο** — μεγαλώνοντας απλά το μέγεθος του προβλήματος, μειώνουμε πολύ το "σκούρο" (μη παραλληλοποιήσιμο) κομμάτι και βλέπουμε σημαντικές επιταχύνσεις.
- Αν όμως το πρόβλημά μας είναι **πολύ ελαφρύ** (μικρός υπολογισμός), τότε θα επιβαρυνόμαστε πολύ περισσότερο από αυτό το σταθερό, μη-παραλληλοποιήσιμο κομμάτι.

### Στόχος μας ως προγραμματιστές: ελαχιστοποίηση του "serial work"
Το πρακτικό μας κόλπο (που ήδη εφαρμόζουμε): **μετράμε μόνο το βασικό for loop** στη χρονομέτρηση, και προσπαθούμε να αποφεύγουμε κώδικα που εκτελείται μόνο από ένα "μηχάνημα"/νήμα ενώ τα υπόλοιπα περιμένουν άπραγα — δηλαδή κοιτάμε πάντα τα **μεγάλα for loops**, που συνήθως επιβαρύνουν περισσότερο την εκτέλεση, και προσπαθούμε να τα παραλληλοποιήσουμε όσο πιο πλήρως γίνεται.

## 27. Μοιραζόμενη Μνήμη — Επίσημος Ορισμός

**Μοιραζόμενη μνήμη**: οι χώροι διευθύνσεων διεργασιών ή νημάτων έχουν **κοινές περιοχές** — δηλαδή αναφέρονται στις ίδιες φυσικές διευθύνσεις. Το `X` του ενός νήματος **είναι** το ίδιο `X` του άλλου.

- Σε **διεργασίες**: δύσκολο να επιτευχθεί (υπάρχουν μηχανισμοί προστασίας μνήμης στα λειτουργικά συστήματα που το εμποδίζουν — αυτό το είδατε στο μάθημα Λειτουργικών Συστημάτων).
- Σε **νήματα**: πολύ πιο εύκολο, αφού μοιράζονται ήδη τον χώρο της ίδιας διεργασίας.
- Στο μάθημα εφαρμόζουμε στην πράξη ό,τι μάθατε θεωρητικά στα Λειτουργικά Συστήματα, τώρα μέσα από προγραμματισμό.

### Πώς κρίνουμε αν μια μεταβλητή είναι "μοιραζόμενη"
Κοιτάμε την **εμβέλεια (scope)** της μεταβλητής — ίδιοι κανόνες με τον ακολουθιακό προγραμματισμό:
- Αν η εμβέλειά της είναι **ορατή από περισσότερα από ένα νήματα/εργασίες** → είναι **μοιραζόμενη/κοινόχρηστη**.
- Σε ακολουθιακό κώδικα λέγαμε "τη βλέπει και η τάδε μέθοδος/αντικείμενο". Σε νηματικό κώδικα, όταν έχουμε πολλά αντικείμενα της ίδιας κλάσης (πολλά threads), λέμε ότι η μεταβλητή "μοιράζεται" ανάμεσά τους.

**Python vs Java**: Στην Python (`multiprocessing`) είναι εύκολο να μοιράσεις μεταβλητές ακόμα και μεταξύ **διεργασιών**, με την ίδια ευκολία όπως μεταξύ νημάτων. Στη Java **δεν** είναι έτσι — γι' αυτό στο μάθημα θα ασχοληθούμε κυρίως με διαμοιρασμό **σε νήματα**.

## 28. Τρεις Βασικοί Τρόποι Διαμοιρασμού Μεταβλητών στη Java

### α) Καθολικές (static) μεταβλητές
Ο πιο απλός τρόπος: δηλώνουμε τη μεταβλητή `static` στην κύρια κλάση· οι εσωτερικές κλάσεις (π.χ. η κλάση του thread) τη "βλέπουν" αυτόματα.

```java
public class MyProgram {
    static int n = 0;   // καθολική/static -> ορατή σε όλα τα εσωτερικά threads

    public static void main(String[] args) {
        // ...
    }

    static class CounterThread extends Thread {
        public void run() {
            for (int i = 0; i < 10000; i++) {
                n = n + 1;   // όλα τα threads μοιράζονται το ΙΔΙΟ n
            }
        }
    }
}
```

**⚠️ Προσοχή:** Επειδή δεν περνάνε "επίσημα" σαν παράμετρος, υπάρχει κίνδυνος **παρενεργειών** (side effects) — μπορεί να ξεχάσεις ότι κάποιο νήμα τροποποιεί μια static μεταβλητή "από μακριά", ειδικά σε μεγαλύτερα προγράμματα. Κάποιοι προγραμματιστές χρησιμοποιούν **ΚΕΦΑΛΑΙΑ ονόματα** για static μεταβλητές ώστε να ξεχωρίζουν οπτικά αμέσως.

### β) Ορίσματα αναφοράς στον constructor (ο πιο ενδεδειγμένος τρόπος)
Ορίζουμε τη μεταβλητή/αντικείμενο κανονικά μέσα στο `main`, και την **περνάμε σαν όρισμα** όταν δημιουργούμε κάθε thread.

```java
public class MyProgram {
    public static void main(String[] args) {
        int[] sharedArray = new int[100];  // τοπική στο main

        Thread[] threads = new Thread[numThreads];
        for (int i = 0; i < numThreads; i++) {
            threads[i] = new MyThread(sharedArray);  // ίδιο array σε όλα -> shared
            threads[i].start();
        }
    }
}
```

Επειδή όλα τα threads παίρνουν **την ίδια αναφορά** στο ίδιο αντικείμενο/array, αυτό είναι μοιραζόμενο. Είναι ο πιο "επίσημος"/κλασικός τρόπος.

**⚠️ Πολύ σημαντική διάκριση: primitives vs objects**
- Αν περάσεις **primitive τύπο** (`int`, `double`, κ.λπ.) σαν όρισμα, περνάει **by value** (τιμή) — **ΔΕΝ** μοιράζεται! Κάθε thread παίρνει **δικό του αντίγραφο**.
- Μόνο **αντικείμενα/arrays** (reference types) περνάνε "by reference" ουσιαστικά — και άρα μοιράζονται πραγματικά.
- Γι' αυτό, αν θες να μοιράσεις έναν απλό αριθμό (`int n`), ο πιο απλός τρόπος είναι η **static** λύση (α) — όχι να τον περάσεις σαν constructor argument.

### γ) Ενδιάμεσος τρόπος: Δομή/κλάση με τα κοινά δεδομένα
Οργανώνουμε τις καθολικές μεταβλητές μέσα σε μια **κλάση** (structure), δημιουργούμε **ένα** αντικείμενο αυτής της κλάσης στο main, και το περνάμε σαν όρισμα (reference) σε όλα τα threads.

```java
class SharedData {
    int n;
    int[] a;
    public SharedData(int size) {
        this.n = 0;
        this.a = new int[size];
    }
}

// στο main:
SharedData data = new SharedData(100);
threads[i] = new MyThread(data);   // όλα μοιράζονται το ΙΔΙΟ αντικείμενο data
```

### δ) Πλήρως αντικειμενοστρεφής τεχνική (η πιο "Java-native")
Η κλάση δεν περιέχει μόνο τα δεδομένα, αλλά και τις **μεθόδους** που εφαρμόζονται πάνω τους (encapsulation) — π.χ. `inc()`, `get()`.

```java
class SharedCounter {
    private int n = 0;
    public synchronized void inc() { n = n + 1; }
    public synchronized int get() { return n; }
}
```

- Αυτή η τεχνική είναι η **πιο ενδεδειγμένη για τη Java** — ακολουθεί τη λογική/φιλοσοφία της γλώσσας (object-oriented).
- **Δεν** είναι τόσο εύκολα εφαρμόσιμη σε γλώσσες όπως η C (δεν έχει native objects/methods με encapsulation).
- Λειτουργεί καλά και σε άλλες αντικειμενοστρεφείς γλώσσες (π.χ. Python).
- Αν δουλεύεις σε C: χρησιμοποίησε structures και πέρνα τα σαν δεδομένα (πιο κοντά στην τεχνική γ).

**Ο καθηγητής θα δείξει και τις 4 τεχνικές στον κώδικα· ο φοιτητής αποφασίζει ποια θα χρησιμοποιήσει.**

## 29. Λεπτομέρεια: static μεταβλητή μέσα σε εσωτερική (nested) κλάση

Πολύ σημαντική διάκριση που μπερδεύει συχνά:

| Πού δηλώνεται το `int n` | Είναι shared; |
|---|---|
| **Static στην κύρια/εξωτερική κλάση** | ✅ Ναι — γνωστή σε όλα τα εσωτερικά threads (πλησιέστερο σε "global" που έχει η Java) |
| **Ως local μεταβλητή μέσα στο `run()`** | ❌ Όχι — τοπική στη μέθοδο, κάθε κλήση έχει δικό της αντίγραφο |
| **Ως instance variable** (μη-static πεδίο) **μέσα στην κλάση του thread** (π.χ. `class CounterThread extends Thread { int n; ... }`) | ❌ Όχι — κάθε **αντικείμενο** (κάθε thread instance) έχει το **δικό του, ξεχωριστό αντίγραφο**. Δεν είναι shared, παρόλο που "μοιάζει" σαν να ανήκει στην κλάση. |
| **Static πεδίο μέσα σε εσωτερική (nested/inner) κλάση, η οποία με τη σειρά της βρίσκεται μέσα σε άλλη κλάση** | Χρειάζεται προσοχή/έλεγχος — ανάλογα με το πού ακριβώς είναι ορατή. Αν η εσωτερική κλάση ήταν **έξω** (top-level), δεν θα ήταν καν γνωστή. |

**Java Memory Model (βασικά, σε σχέση με JVM):**
- **Heap**: εκεί ζουν τα αντικείμενα (objects), και **static** μεταβλητές της κλάσης.
- **Thread Stack**: κάθε νήμα έχει τη δική του στοίβα, όπου ζουν οι **τοπικές μεταβλητές** και οι **παράμετροι μεθόδων**.
- Οι static μεταβλητές είναι στο Heap → **προσβάσιμες από όλα τα threads**.
- Οι τοπικές μεταβλητές/παράμετροι είναι στη Stack **κάθε** thread ξεχωριστά → **όχι** μοιραζόμενες (εκτός αν είναι reference σε κοινό αντικείμενο).

## 32. Παράδειγμα Static Demo — Πλήρης Ανάλυση των 4 Τρόπων (στην πράξη)

Ο καθηγητής έδειξε στον κώδικα (φάκελος `SharedCounter`) τις 4 τεχνικές διαμοιρασμού πάνω σε πραγματικό, τρέξιμο πρόγραμμα:

### α) Static πεδίο στην εξωτερική κλάση
```java
public class SharedCounterDemo {
    static int n = 0;   // static στην ΚΥΡΙΑ κλάση -> shared σε όλα τα εσωτερικά threads

    static class CounterThread extends Thread {
        public void run() {
            for (int i = 0; i < 10000; i++) n = n + 1;
        }
    }
}
```
✅ Μοιράζεται — **αλλά μόνο επειδή** το `CounterThread` είναι **εσωτερική (nested) κλάση** μέσα στην κύρια. Αν η κλάση `CounterThread` ήταν **έξω** (top-level, ξεχωριστό αρχείο/ορισμός), δεν θα έβλεπε το `n` καν.

**Αξιολόγηση του καθηγητή**: Αυτή η τεχνική **δεν αρέσει** γενικά ("δεν μ' αρέσει") — δημιουργεί side effects, δύσκολο να διαβαστεί/παρακολουθηθεί. Πρέπει να χρησιμοποιείται **με μεγάλη φειδώ**.

### β) Πλήρως αντικειμενοστρεφής (κλάση με δεδομένα + μέθοδο)
```java
class SharedCounter {
    int n = 0;
    public void increment() { n = n + 1; }
}

// main:
SharedCounter counter = new SharedCounter();
threads[i] = new CounterThread(counter);   // περνάει reference
```
Στο `run()` του thread: `counter.increment();`
- Εδώ το `n` **δεν χρειάζεται να είναι static** — μοιράζεται επειδή όλα τα threads έχουν **αναφορά στο ίδιο, μοναδικό** αντικείμενο `counter`.
- Η αύξηση γίνεται **μέσα** στο αντικείμενο `SharedCounter` (`increment()`), όχι στο κυρίως πρόγραμμα.

### γ) Ενδιάμεση τεχνική — μοιραζόμενη δομή ΧΩΡΙΣ μέθοδο
```java
class SharedData {
    int n;
}

// main:
SharedData data = new SharedData();
threads[i] = new CounterThread(data);
```
Στο `run()`: `data.n = data.n + 1;` (προσπελάζουμε απευθείας το **field** του αντικειμένου, όχι μέσω μεθόδου).
- Ισοδύναμο με **struct** στη C — δομή δεδομένων χωρίς ενσωματωμένη λογική.
- Χρησιμοποιείται σε γλώσσες που **δεν** έχουν αντικειμενοστρεφή χαρακτηριστικά (καθαρή C).

### δ) Ορίσματα με primitive τιμή — ΤΟ ΛΑΘΟΣ ΠΟΥ ΠΡΕΠΕΙ ΝΑ ΑΠΟΦΥΓΕΙΣ
```java
class CounterThread extends Thread {
    int n;   // instance variable, ΟΧΙ static
    public CounterThread(int n) { this.n = n; }
    public void run() {
        for (int i = 0; i < 10000; i++) n = n + 1;
    }
}

// main:
int n = 0;
for (int i = 0; i < numThreads; i++) {
    threads[i] = new CounterThread(n);   // περνάει την ΤΙΜΗ 0, όχι αναφορά!
    threads[i].start();
}
// μετά το join: το "n" στο main ΠΑΡΑΜΕΝΕΙ 0 !!
```
**Γιατί συμβαίνει αυτό:** Το `int n` είναι **primitive** τύπος. Όταν περνάει σαν constructor argument, περνάει **by value** (αντιγράφεται η τιμή). Κάθε thread παίρνει **δικό του ξεχωριστό αντίγραφο** του `n` — αυξάνει το **δικό του** αντίγραφο 10.000 φορές, αλλά αυτό **δεν** επηρεάζει καθόλου το `n` του main ή των άλλων threads.

**Αυτό ήταν πραγματικό θέμα εξετάσεων** στο μάθημα: *"Δίνεται τέτοιος κώδικας — ποια θα είναι η τελική τιμή του n στο main;"* Η σωστή απάντηση είναι **0** (ή η αρχική τιμή), όχι το άθροισμα όλων των αυξήσεων.

**Πιθανή λύση αν θες να αποφύγεις primitives:** Στη Java μπορείς να ορίσεις τον αριθμό σαν **αντικείμενο** (`Integer` object) αντί για `int` primitive — τότε περνάει σαν αναφορά. Ο καθηγητής το ανέφερε ως περιέργεια/επιλογή, **όχι** σαν συνιστώμενη πρακτική. Ο πιο απλός κανόνας: **όταν έχεις primitive τιμή που πρέπει να μοιραστεί, χρησιμοποίησε static.**

### Στη γλώσσα C (σύγκριση)
- Δεν υπάρχουν κλάσεις/μέθοδοι όπως στη Java.
- Μπορείς να κάνεις: (1) καθολική (global) μεταβλητή, ή (2) `struct` + δείκτης (pointer) που περνάει σαν όρισμα στο `pthread_create()`.
- **Δεν** μπορείς να έχεις "μέθοδο μέσα σε αντικείμενο" (καμία encapsulation) — αυτό είναι το πλεονέκτημα της Java/αντικειμενοστρεφών γλωσσών: **information hiding** — κρύβουμε την πολυπλοκότητα μέσα στο μοιραζόμενο αντικείμενο, το υπόλοιπο πρόγραμμα δεν χρειάζεται να αλλάξει.

### Ακόμα πιο "εξωτικοί" τρόποι πρόσβασης (γενικά αποφεύγονται)
- Πρόσβαση από εξωτερικό κώδικα μέσω `ClassName.field` ή `object.publicField`, όταν το πεδίο **δεν** είναι `private`.
- Ο καθηγητής τα ανέφερε ως ύπαρξη ("μπορούν να γίνουν") αλλά **δεν τα συνιστά** — προτιμήστε τους 4 βασικούς, καθαρούς τρόπους.

## 33. Το Κρίσιμο Πρόβλημα: Ακολουθιακή Συνέπεια (Sequential Consistency)

### Πότε έχουμε πρόβλημα και πότε όχι
- Όσο τα νήματα **δεν μοιράζονται τίποτα** μεταξύ τους → κανένα πρόβλημα, τρέχουν ανεξάρτητα.
- Όσο τα νήματα κάνουν **μόνο** ανάγνωση (reads) σε μοιραζόμενες μεταβλητές → κανένα πρόβλημα.
- Το πρόβλημα εμφανίζεται όταν έχουμε **ανάγνωση+εγγραφή** ή **εγγραφή+εγγραφή** στην **ίδια** μοιραζόμενη μεταβλητή, από διαφορετικά νήματα.

### "Δεν πειράζει" vs "πειράζει" — η διαφορά
- Αν δύο νήματα απλά **τυπώνουν** μηνύματα (π.χ. "Γεια σου, είμαι το νήμα 1", "Γεια σου, είμαι το νήμα 2") σε τυχαία σειρά → **δεν πειράζει** ουσιαστικά, κάθε εκτύπωση από μόνη της είναι σωστή/έχει νόημα, απλά η **σειρά** τους δεν είναι προβλέψιμη. Δεν χάνουμε τίποτα σημαντικό.
- Αν όμως τα νήματα **τροποποιούν** μια κοινή μεταβλητή → η σειρά **έχει σημασία**, και μπορεί να καταλήξουμε σε **λάθος τελικό αποτέλεσμα**.

### Ορισμός: Ακολουθιακή Συνέπεια
Μέσα σε **ένα** νήμα, η σειρά εκτέλεσης εντολών είναι πάντα σωστή/συνεπής (ακολουθιακή). Αλλά όταν **πολλά** νήματα εκτελούνται παράλληλα και "μπλέκονται" (interleave), η **συνολική** σειρά με την οποία γίνονται οι εγγραφές/αναγνώσεις στη μοιραζόμενη μνήμη **δεν είναι** εγγυημένη ούτε προβλέψιμη.

### Παράδειγμα με 4 νήματα και μια μοιραζόμενη μεταβλητή
- Νήμα 1: γράφει την τιμή 100
- Νήμα 2: γράφει την τιμή 200
- Νήμα 3: διαβάζει
- Νήμα 4: διαβάζει

Πιθανές **διατάξεις εκτέλεσης** (κάθε μία «ακολουθιακά συνεπής» μέσα στο κάθε νήμα, αλλά διαφορετική "διαπλοκή" — **interleaving**):
- Γράφει 100 → Γράφει 200 → Διαβάζει 200 → Διαβάζει 200
- Γράφει 100 → Διαβάζει 100 → Γράφει 200 → Διαβάζει 200
- Γράφει 200 → Γράφει 100 → ...

Αυτό το φαινόμενο λέγεται **διαπλοκή ιχνών (interleaving of traces)** — είναι η ρίζα του προβλήματος που προσπαθούμε να λύσουμε με τον αμοιβαίο αποκλεισμό.

**Σημαντικό**: Αυτό το πρόβλημα **δεν εξαφανίζεται** ούτε καν με **έναν** μόνο επεξεργαστή — εμφανίζεται εξαιτίας των **χρονοδιακοπών** και της **μη-αιτιοκρατικής δρομολόγησης** (ο scheduler μπορεί να διακόψει ένα νήμα οποιαδήποτε στιγμή). Με πολλούς επεξεργαστές, το πρόβλημα εντείνεται επίσης λόγω του ότι οι εγγραφές στη μνήμη γίνονται αναγκαστικά σειριακά στο hardware.

## 34. Συνοχή Μνήμης (Coherence) vs Συνέπεια Μνήμης (Consistency)

Δύο ξεχωριστές, σημαντικές έννοιες:

| Όρος | Ορισμός | Ποιος το λύνει |
|---|---|---|
| **Συνοχή (Coherence)** | Σε κάθε χρονική στιγμή, σε όλη την ιεραρχία της μνήμης πρέπει να υπάρχει **μόνο μία έγκυρη τιμή** για κάθε μεταβλητή | Λύνεται από το **hardware** (πρωτόκολλα cache coherence) — όταν μια μεταβλητή αλλάζει κάπου, οι υπόλοιπες κρυφές μνήμες (caches) ακυρώνουν τα παλιά τους αντίγραφα και παίρνουν τη νέα τιμή. Αν δύο ταυτόχρονες αλλαγές γίνουν, μόνο η μία επικρατεί, η άλλη πρέπει να επαναληφθεί. |
| **Συνέπεια (Consistency)** | Όταν πολλά νήματα εκτελούν παράλληλα με μοιραζόμενες μεταβλητές, **πρέπει να βλέπουν την ίδια χρονική διάταξη των μεταβολών** — οι τιμές να είναι ίδιες παντού, με την ίδια σειρά | **Δική μας ευθύνη ως προγραμματιστές** — πρέπει εμείς να επιβάλλουμε τους κανόνες σειράς με μηχανισμούς συγχρονισμού |

**Αυτό που μας απασχολεί περισσότερο στο μάθημα είναι η Συνέπεια (Consistency)** — το coherence το χειρίζεται αυτόματα το hardware.

### Ασθενής Συνέπεια (Weak Consistency)
Η τεχνική που ακολουθούμε: ορίζουμε **συγκεκριμένα σημεία** στο πρόγραμμα όπου επιβάλλουμε συγχρονισμό — "εδώ πρέπει όλοι να μάθουν τις αλλαγές που έχουν γίνει μέχρι τώρα" — και ανάμεσα σε αυτά τα σημεία, το σύστημα είναι ελεύθερο. Αυτό μας εγγυάται ότι:
- Ό,τι έχει συμβεί **πριν** το σημείο συγχρονισμού, το γνωρίζουν όλοι μετά από αυτό.
- Ό,τι συμβαίνει **μετά**, θα έχει τη σωστή τιμή.

## 35. Συνθήκη Ανταγωνισμού (Race Condition) & Κρίσιμο Τμήμα (Critical Section)

### Ορισμός
Έχουμε **συνθήκη ανταγωνισμού (race condition)** όταν **δύο ή περισσότερα νήματα τροποποιούν την ίδια μοιραζόμενη μεταβλητή**.

Οι εντολές που κάνουν αυτή την τροποποίηση ονομάζονται **κρίσιμο τμήμα (critical section)**.

### Πρακτική μεθοδολογία εντοπισμού
1. Βρες **ποιες μεταβλητές είναι μοιραζόμενες**.
2. Για κάθε μοιραζόμενη μεταβλητή, έλεγξε τι κάνουν τα νήματα πάνω της:
   - **Μόνο αναγνώσεις (read-read)** → κανένα πρόβλημα.
   - **Ανάγνωση + Εγγραφή (read-write)**, ή **Εγγραφή + Εγγραφή (write-write)** → **ΈΧΟΥΜΕ race condition**.
3. Σημείωσε τις εντολές που προκαλούν το πρόβλημα → αυτό είναι το **κρίσιμο τμήμα**.
4. Εφάρμοσε **αμοιβαίο αποκλεισμό** σε αυτό το τμήμα.

### Αμοιβαίος Αποκλεισμός (Mutual Exclusion)
Επιτρέπουμε **μόνο ένα νήμα τη φορά** να μπει και να εκτελέσει το κρίσιμο τμήμα, ώστε η μία τροποποίηση να μην "συγκρούεται" με μια άλλη ταυτόχρονη.

**⚠️ Κόστος:** Ο αμοιβαίος αποκλεισμός **προκαλεί καθυστέρηση** — ουσιαστικά **σειριοποιεί** (κάνει ακολουθιακό) το πρόγραμμα σε εκείνο το σημείο. Γι' αυτό πρέπει να είμαστε **πολύ προσεκτικοί** ώστε να **μην** βάζουμε υπερβολικά μεγάλα κρίσιμα τμήματα — μόνο ό,τι πραγματικά χρειάζεται προστασία.

### Γιατί αξίζει ο παραλληλισμός παρόλο που κάπου σειριοποιούμε (σχέση με Amdahl)
Ερώτηση φοιτητή: *"Αφού περιμένουμε να τελειώσει ο ένας για να μπει ο άλλος, πού είναι το κέρδος του παραλληλισμού;"*

**Απάντηση:** Σε ένα πραγματικό πρόγραμμα με π.χ. 100 γραμμές κώδικα, το κρίσιμο τμήμα μπορεί να είναι μόνο **λίγες** γραμμές (π.χ. 5), ενώ οι υπόλοιπες **95** είναι "καθαρές" — τρέχουν πλήρως παράλληλα χωρίς κανένα πρόβλημα. Το κέρδος έρχεται από αυτές τις 95 γραμμές. Το κόστος πληρώνεται μόνο στο μικρό κρίσιμο τμήμα (5 γραμμές). **Λάθος πρακτική** θα ήταν να "κλειδώσεις" ολόκληρο το πρόγραμμα — τότε το κάνεις εντελώς ακολουθιακό και χάνεις όλο το όφελος.

**Ο πρακτικός στόχος μας**: να **ελαχιστοποιούμε το μέγεθος του κρίσιμου τμήματος** — να διακρίνουμε καθαρά ποιο κομμάτι του προγράμματος χρειάζεται προστασία και ποιο όχι, και να προστατεύουμε **μόνο** το απαραίτητο.

## 36. Παράδειγμα: Πραγματική Αποτυχία στο SharedCounter (χωρίς κλείδωμα)

Ο καθηγητής έτρεξε το `SharedCounter` (χωρίς lock) με πολλά νήματα, καθένα προσθέτοντας 1, 10.000 φορές. Αναμενόμενο αποτέλεσμα (π.χ. με 5 νήματα): **50.000**. Πραγματικό αποτέλεσμα: **διάφορες τυχαίες, λάθος τιμές** κάθε φορά.

### Γιατί συμβαίνει: Η αύξηση `n = n + 1` ΔΕΝ είναι atomic
Η φαινομενικά απλή εντολή `n = n + 1` **δεν** είναι μία εντολή στη γλώσσα μηχανής — είναι **τρεις**:
1. **Φόρτωσε** (load) την τρέχουσα τιμή του `n`
2. **Αύξησε** (increment) την τιμή
3. **Σώσε** (store) τη νέα τιμή πίσω

Κάθε μία από αυτές τις 3 εντολές είναι **atomic** (αδιαίρετη — δεν μπορεί να διακοπεί στη μέση), αλλά η **τριάδα** μαζί **δεν είναι** atomic — μπορεί να διακοπεί ανάμεσα σε αυτές.

**Παράδειγμα απώλειας ενημέρωσης (lost update):**
```
Thread A: Φόρτωσε n (=5)
Thread B: Φόρτωσε n (=5)     <- και τα δύο βλέπουν 5, πριν προλάβει κανείς να γράψει
Thread A: Αύξησε -> 6
Thread B: Αύξησε -> 6
Thread A: Σώσε n = 6
Thread B: Σώσε n = 6         <- ΧΑΘΗΚΕ μία αύξηση! Έπρεπε να είναι 7.
```

**Θέμα εξετάσεων (αναφέρθηκε ρητά από τον καθηγητή):** *"Έχουμε δύο νήματα, το ένα κάνει `myData++` και το άλλο `myData--`, μέσα σε loop 10 επαναλήψεων το καθένα, ξεκινώντας από 0. Τι τιμή θα έχει το `myData` στο τέλος;"*
**Σωστή απάντηση: ΔΕΝ ΓΝΩΡΙΖΟΥΜΕ** — δεν είναι εγγυημένα 0, ούτε κανένα άλλο συγκεκριμένο νούμερο. Εξαρτάται εντελώς από τη μη-προβλέψιμη σειρά interleaving των load/increment(ή decrement)/store εντολών. (Παλαιότερα ο καθηγητής έβαλε αυτό ακριβώς ως ερώτηση εξετάσεων και πολλοί φοιτητές απάντησαν λάθος "0" ή "10" με σιγουριά — η σωστή απάντηση είναι ότι είναι **απρόβλεπτο**.)

**Βασικό μήνυμα:** Το λειτουργικό σύστημα **δεν** μπορεί να "διορθώσει" αυτό μόνο του — δεν ξέρει τι προσπαθεί να κάνει το πρόγραμμά σου λογικά. Είναι **δική σου ευθύνη ως προγραμματιστή** να επιβάλλεις τη σωστή σειρά.

## 37. Δεύτερο Σενάριο Συνθήκης Ανταγωνισμού: Σηματοδοσία (Signaling)

Πέρα από το "ποιος μπαίνει" (αμοιβαίος αποκλεισμός), υπάρχει και το ζήτημα **ποιος μπαίνει πρώτος** — αυτό λέγεται **σηματοδοσία (signaling)**.

- Παράδειγμα: ένα νήμα Α πρέπει να διαβάσει δεδομένα **μετά** που κάποιο νήμα Β τα έχει γράψει — όχι πριν.
- Λύνεται με μηχανισμούς όπως **P/V σηματοφόρους (semaphores)**, τους οποίους ίσως έχετε δει στο μάθημα Λειτουργικών Συστημάτων.
- **Θα καλυφθεί σε επόμενο μάθημα** — δεν είναι το ίδιο θέμα με τον απλό αμοιβαίο αποκλεισμό.

### Barrier (Φράγμα) — προαναφέρεται, θα δούμε αναλυτικά αργότερα
- Το **barrier** λέει: "όλα τα νήματα πρέπει να φτάσουν σε αυτό το σημείο πριν συνεχίσει οποιοδήποτε" — όποιο φτάσει νωρίτερα, **περιμένει** τα υπόλοιπα.
- **Διαφορά από αμοιβαίο αποκλεισμό**: το barrier **δεν** καθορίζει ποιος μπαίνει πρώτος σε ένα κρίσιμο τμήμα — απλά συγχρονίζει **όλα** τα νήματα σε ένα κοινό σημείο.
- Είναι **μηχανισμός συγχρονισμού**, όχι αμοιβαίου αποκλεισμού.

## 38. Μηχανισμοί Χαμηλού Επιπέδου (Hardware/Γλώσσα Μηχανής)

### Ατομικές εντολές
Οι γλώσσες μηχανής προσφέρουν **ειδικές atomic (αδιαίρετες) εντολές** για να υλοποιήσουν lock/unlock χωρίς πρόβλημα:
- **Test-and-Set**: η πιο απλή/κλασική.
- **Compare-and-Swap (CAS)**
- **Load-Linked / Store-Conditional**

Αυτές δεν αναλύθηκαν σε βάθος — απλή αναφορά ύπαρξης.

### Spin Locks — Πρόβλημα του "Busy Waiting"
Τα κλειδώματα σε πολύ χαμηλό επίπεδο κάνουν **spinning** (ενεργός αναμονή): το πρόγραμμα **συνεχώς ρωτάει** "μπορώ να πάρω το κλείδωμα;" σε βρόχο, καταναλώνοντας άσκοπα χρόνο CPU όσο περιμένει. Γι' αυτό λέγονται **spin locks**.

### Interrupts στο επίπεδο του λειτουργικού συστήματος
- Χρησιμοποιούνται **μόνο** από το λειτουργικό σύστημα (π.χ. σε context switch, "μη με διακόπτει κανείς αυτή τη στιγμή").
- **Δεν** μπορούμε (ούτε πρέπει) να τα χρησιμοποιήσουμε εμείς ως προγραμματιστές εφαρμογών — θα σήμαινε δικαίωμα να σταματήσουμε όλα τα προγράμματα στο σύστημα, κάτι που απαιτεί δικαιώματα λειτουργικού συστήματος.
- Τρεις τύποι interrupt: system calls, software interrupts, hardware interrupts. Στο επίπεδό μας μιλάμε κυρίως για software interrupts.
- Η λογική τους χρησιμοποιείται εσωτερικά στην υλοποίηση του `signal`/`wait` (θα το δούμε αργότερα).

### Φράκτες Μνήμης (Memory Fences/Barriers)
Παράδειγμα στη Java: η λέξη-κλειδί **`volatile`**.

```java
static volatile int n = 0;
```

- Το `volatile` **δεν είναι μεταβλητή** — είναι **προσδιοριστικό (qualifier)** μιας μεταβλητής.
- Σημαίνει: "κάθε αλλαγή σε αυτή τη μεταβλητή, πέρασέ την **αμέσως** σε όλη την ιεραρχία μνήμης — μην την κρατάς σε τοπική cache — ώστε όλα τα νήματα να τη μαθαίνουν γρήγορα."
- **ΠΡΟΣΟΧΗ — Πολύ σημαντικό**: Το `volatile` **λύνει μόνο το πρόβλημα ορατότητας (visibility)**, **ΔΕΝ λύνει το πρόβλημα σωστής σειράς εκτέλεσης (ordering)**. Αν τρέξεις έναν κώδικα σαν τον `SharedCounter` βάζοντας απλά `volatile` στο `n`, **θα εξακολουθεί να δίνει λάθος αποτέλεσμα** — γιατί το πρόβλημα δεν είναι ότι τα νήματα δεν βλέπουν τις αλλαγές γρήγορα, είναι ότι η τριάδα load-increment-store παραμένει μη-atomic.
- Οι φράκτες μνήμης είναι χρήσιμοι μόνο σε **πολύ ειδικές περιπτώσεις**, όχι ως γενική λύση όπως τα κλειδώματα.

### Δημιουργία/Τερματισμός Νημάτων ως σημεία συγχρονισμού
Επίσης αποτελούν φυσικά "σημεία αναφοράς" — όσα συνέβησαν πριν από ένα `start()` ή ένα `join()` είναι εγγυημένα ορατά μετά από αυτό.

## 39. Μηχανισμοί Υψηλού Επιπέδου: Locks & Semaphores

Δύο **καθολικοί** (universal, σε κάθε γλώσσα) μηχανισμοί αμοιβαίου αποκλεισμού:

### α) Κλειδώματα (Locks)
- Δηλώνονται σαν κανονικές μοιραζόμενες μεταβλητές.
- Δύο **ατομικές (atomic)** ενέργειες: **`lock()`** και **`unlock()`**.
- **Αποτυχία να πάρεις το lock → Αναστολή (blocking), ΟΧΙ ενεργός αναμονή (busy waiting)**. Το νήμα "κοιμάται", και ξυπνάει όταν γίνει `unlock()` — αλλά **δεν** μπαίνει αυτόματα μέσα, **ξαναπροσπαθεί** να πάρει το lock (γιατί μπορεί να υπάρχουν κι άλλα ενδιαφερόμενα νήματα).
- **Λειτουργεί επίσης σαν φράκτης μνήμης**: ό,τι έχει αλλάξει πριν το `unlock()` γίνεται ορατό σε όλους μετά.

### Πρακτικός κανόνας Java: Ζευγαρώνουμε lock με τη μεταβλητή
```java
static int n = 0;
static Lock lock = new ReentrantLock();

// στο run():
lock.lock();
try {
    n = n + 1;
} finally {
    lock.unlock();
}
```
**Συμβουλή**: Βάζουμε το `lock` **ακριβώς κάτω** από τη μεταβλητή που προστατεύει, ώστε να θυμόμαστε εύκολα ποιο lock αναφέρεται σε ποια μεταβλητή. **Δεν** χρησιμοποιούμε το ίδιο lock για άσχετες μεταβλητές — θα μπερδευτούμε.

### Οι ίδιοι 3 τρόποι εφαρμόζονται και εδώ
1. **Static lock** (καθολικό, μαζί με το static `n`)
2. **Lock μέσα σε δομή/structure** που περνιέται σαν όρισμα
3. **Lock μέσα σε πλήρες OOP αντικείμενο**, μαζί με τα δεδομένα και τη μέθοδο `inc()`

### `try/finally` γύρω από lock/unlock — Γιατί είναι υποχρεωτικό
Το `finally` **εξασφαλίζει** ότι το `unlock()` θα εκτελεστεί **οπωσδήποτε**, ακόμα κι αν:
- Προκύψει exception μέσα στο κρίσιμο τμήμα
- Γίνει πρόωρος τερματισμός (`return`) μέσα στο try block

Χωρίς αυτό, ένα νήμα θα μπορούσε να "κρατήσει" το κλείδωμα για πάντα (deadlock), αφήνοντας όλα τα υπόλοιπα νήματα κολλημένα.

### "Δικαιοσύνη" (Fairness) στα locks
- Γενικά, τα (απλά) locks **δεν εγγυώνται** συγκεκριμένη σειρά (ποιος μπαίνει πρώτος) — μπαίνουν με **τυχαία σειρά**.
- Η Java επιτρέπει **προαιρετικά** να ορίσεις ένα lock ως **"δίκαιο" (fair)**:
  ```java
  Lock lock = new ReentrantLock(true);   // true = fair lock, FIFO ουρά
  ```
- Αυτό είναι **ιδιαιτερότητα της Java**, όχι κάτι γενικό σε όλες τις γλώσσες.
- Ακόμα κι όταν δεν είναι "fair" σε αυστηρή σειρά, οι γλώσσες γενικά εγγυώνται ότι δεν θα έχεις **λιμοκτονία (starvation)** — δηλαδή δεν θα περιμένεις επ' άπειρον, απλά όχι με εγγυημένη σειρά.

### β) Δυαδικοί Σηματοφόροι (Binary Semaphores / Mutex)
- Τύπος δεδομένων με τιμές **μόνο 0 ή 1** (binary — αντίθετα από τον γενικό counting semaphore που παίρνει κι άλλες τιμές).
- Ενέργειες: **`P` / `V`**, ή αλλιώς **`acquire` / `release`**, ή **`down` / `up`** (ανάλογα με τη γλώσσα/βιβλιοθήκη) — όλα ίδια λογική.
- **Διαφορά από το lock**: όταν γίνεται `V`/`release`, ο επόμενος στην **εσωτερική ουρά** μπαίνει **κατευθείαν** — δεν χρειάζεται να ξανα-ελέγξει/ξανα-ζητήσει.
- Ο σηματοφόρος έχει **επίσημη** έννοια δίκαιου (fair/strong) vs μη-δίκαιου (weak):
  - **Ισχυρός/Δίκαιος σηματοφόρος**: δουλεύει με **FIFO** ουρά — όποιος ζήτησε πρώτος, μπαίνει πρώτος.
  - **Ασθενής σηματοφόρος**: τυχαία σειρά, σαν το απλό lock.

### Java syntax για Semaphore
```java
import java.util.concurrent.Semaphore;
Semaphore sem = new Semaphore(1);   // binary semaphore

sem.acquire();
try {
    n = n + 1;
} finally {
    sem.release();
}
```
Το `acquire()` έχει `try/catch(InterruptedException)` γιατί, αν δεν πάρεις το semaphore, μπαίνεις σε αναστολή (blocked) — και αναστολή σημαίνει ότι μπορεί να δεχτείς interrupt.

## 40. Πόσα Κλειδώματα Χρειαζόμαστε; — Κανόνας: "Κλειδώνουμε Μεταβλητή, Όχι Ενέργεια"

**Ερώτηση φοιτητή**: *"Μπορούμε να έχουμε δύο διαφορετικά locks — ένα για την πρόσθεση, ένα για την αφαίρεση;"*

**Απάντηση — ΟΧΙ, λάθος σκέψη:** Το lock **δεν** κλειδώνει μια "ενέργεια" (π.χ. "πρόσθεση"). Κλειδώνει μια **μεταβλητή/δομή δεδομένων**. Αν έχεις μια μοιραζόμενη μεταβλητή που τροποποιείται τόσο από αυξήσεις όσο και από μειώσεις (π.χ. μετρητής επισκεπτών σε κατάστημα: κάποιες πόρτες αυξάνουν, κάποιες μειώνουν), **όλες** οι ενέργειες πάνω σε αυτή τη μεταβλητή πρέπει να χρησιμοποιούν **το ίδιο** lock — αλλιώς δεν προστατεύεται πραγματικά η μεταβλητή (θα μπορούσαν να συγκρουστούν μια αύξηση με μια μείωση ταυτόχρονα, αφού έχουν διαφορετικά κλειδιά).

**Παράδειγμα τραπεζικού λογαριασμού**: Ανάληψη, κατάθεση, εμφάνιση υπολοίπου — όλα διαβάζουν/γράφουν την **ίδια** μεταβλητή υπόλοιπο. Άρα **όλα** πρέπει να χρησιμοποιούν **ένα κοινό** lock. Ακόμα και μια απλή **εκτύπωση** του υπολοίπου (`print`), αν συμβεί ενόσω τρέχει μια συναλλαγή, μπορεί να δώσει άκυρη/ενδιάμεση τιμή — άρα τυπικά χρειάζεται κι αυτή προστασία.

### Πόσα locks μπορούμε να έχουμε συνολικά
Όσα χρειαζόμαστε — **ένα ανά ανεξάρτητη μεταβλητή/δομή** που θέλουμε να προστατέψουμε. Αν έχεις πολλές ανεξάρτητες μεταβλητές (που δεν επηρεάζουν η μία την άλλη), βάζεις **ξεχωριστό** lock για καθεμιά — έτσι δεν "μπλοκάρουν" άσκοπα η μία εξαιτίας της άλλης, βελτιώνοντας την παραλληλία.

**Παράδειγμα λεπτομερούς κλειδώματος**: Έναν πίνακα μπορείς να τον κλειδώσεις **συνολικά** (ένα lock για όλο τον πίνακα) ή **ανά γραμμή** (ξεχωριστό lock ανά γραμμή) — αν οι τροποποιήσεις σε διαφορετικές γραμμές είναι πραγματικά ανεξάρτητες, το ανά-γραμμή κλείδωμα επιτρέπει **περισσότερο** πραγματικό παραλληλισμό (θα το δούμε αναλυτικά σε επόμενο μάθημα). Θα δούμε επίσης ότι Java και άλλες γλώσσες προσφέρουν **έτοιμες, ήδη thread-safe δομές δεδομένων** (π.χ. concurrent collections) που έχουν ήδη ενσωματωμένη τη λογική κλειδώματος — δεν χρειάζεται πάντα να τα φτιάχνουμε όλα από την αρχή.

## 41. Το `synchronized` της Java — Ο "Επίσημος" Τρόπος (χωρίς βιβλιοθήκη)

Η Java έχει **δύο** ομάδες μηχανισμών:
1. **`synchronized` / `wait` / `notify`** — **ενσωματωμένα στην ίδια τη γλώσσα** (δεν χρειάζεται `import`).
2. **`java.util.concurrent`** — εξωτερική βιβλιοθήκη με πολύ περισσότερα εργαλεία (Locks, Semaphores, κ.λπ., όπως είδαμε παραπάνω).

### Πώς δουλεύει το `synchronized`
- **Κάθε αντικείμενο στη Java έχει ένα "κρυφό" ενσωματωμένο κλείδωμα** (intrinsic lock / monitor), το οποίο **ενεργοποιείται μόνο** όταν χρησιμοποιήσουμε τη λέξη `synchronized`.
- `synchronized` **δεν σημαίνει "συγχρονισμός" με την έννοια της σειράς** — σημαίνει **αμοιβαίος αποκλεισμός**! (σημαντική διευκρίνιση/λεκτική παγίδα του καθηγητή)

### Δύο μορφές χρήσης

**Σε επίπεδο μεθόδου:**
```java
class SharedCounter {
    int n = 0;
    public synchronized void increment() {   // κλειδώνει το ΑΝΤΙΚΕΙΜΕΝΟ SharedCounter
        n = n + 1;
    }
}
```
Όλα τα νήματα που καλούν `increment()` πάνω στο **ίδιο αντικείμενο** πρέπει να πάρουν το κλείδωμα εκείνου του αντικειμένου — μόνο ένα τη φορά.

**Σε επίπεδο block (μόνο ένα κομμάτι κώδικα μέσα στη μέθοδο):**
```java
public void increment() {
    synchronized(this) {   // κλειδώνει "this" - το τρέχον αντικείμενο
        n = n + 1;
    }
}
```
Εδώ ορίζουμε **ρητά** ποιο αντικείμενο κλειδώνουμε (`this`, ή οποιοδήποτε άλλο αντικείμενο θέλουμε).

### Σύγκριση: `synchronized` vs `Lock` (util.concurrent)

| | `Lock`/`ReentrantLock` | `synchronized` |
|---|---|---|
| Χρειάζεται import | Ναι (`java.util.concurrent.locks`) | Όχι — built-in |
| Ρητό κλείδωμα | Δηλώνεις ξεχωριστό `Lock` αντικείμενο | Χρησιμοποιεί το ενσωματωμένο "κρυφό" lock του αντικειμένου |
| Σύνταξη | `lock.lock(); try {...} finally {lock.unlock();}` | `synchronized(obj) { ... }` ή `synchronized` στη δήλωση μεθόδου |
| Ευελιξία | Περισσότερη (timeout, interruptible, fairness) | Λιγότερη, αλλά πιο απλό/κομψό |

**Πρακτική προειδοποίηση**: Οι φοιτητές έχουν την τάση να "πετάνε" `synchronized` "όπου να 'ναι" επειδή φαίνεται εύκολο — αλλά κάθε φορά που το χρησιμοποιείς, **πρέπει να κλειδώνεις συγκεκριμένο, σαφές αντικείμενο**. Δεν αρκεί απλά να το βάλεις "και να δουλέψει η μέθοδος" χωρίς σκέψη για ποιο αντικείμενο προστατεύεται.

**Ζήτημα που θα εξεταστεί σε επόμενο μάθημα**: τι κάνεις όταν **δεν** έχεις ξεκάθαρο αντικείμενο να κλειδώσεις (π.χ. έχεις μόνο ένα "γυμνό" primitive int) — εκεί χρειάζεται ειδικός χειρισμός με `synchronized`.

   - `synchronized` (built-in Java)
4. Επαλήθευσε ότι **κάθε** εκδοχή δίνει πλέον **σωστό, σταθερό αποτέλεσμα** σε κάθε τρέξιμο (όχι πια τυχαία λάθη).

**Bonus ιδέα που πρότεινε φοιτητής (και ο καθηγητής ενέκρινε ως καλή άσκηση):** Δοκίμασε το ίδιο πρόβλημα με **δύο διαφορετικά είδη νημάτων** πάνω στην ίδια μεταβλητή — ένα που κάνει `n++` (adder/incrementor) και ένα που κάνει `n--` (subtractor) — και βεβαιώσου ότι και τα δύο είδη νημάτων χρησιμοποιούν **το ίδιο** lock (αφού προστατεύουν την ίδια μεταβλητή).

**Σύνδεση με τη μεγαλύτερη εργαστηριακή εργασία** (SharedCounterExercise, που ήδη συζητήσαμε): αυτή η άσκηση με το απλό `SharedCounter` είναι το **"εμβληματικό" (paradigmatic) πρόβλημα** πάνω στο οποίο θα εφαρμόσεις ό,τι έμαθες εδώ, στα δικά σου δύο πιο σύνθετα αρχεία (`SharedCounterArrayGlobal`, `SharedCounterArrayGlobalWhile`).

## 43. Ανακεφαλαίωση — Μέρος Γ

| Έννοια | Σε μία πρόταση |
|---|---|
| **Race condition** | Δύο+ νήματα τροποποιούν την ίδια μοιραζόμενη μεταβλητή |
| **Critical section (κρίσιμο τμήμα)** | Οι εντολές που προκαλούν το race condition — χρειάζονται προστασία |
| **Ακολουθιακή συνέπεια** | Μέσα σε ένα νήμα πάντα σωστή σειρά· ανάμεσα σε νήματα, όχι εγγυημένη |
| **Interleaving (διαπλοκή ιχνών)** | Το "ανακάτεμα" εντολών από διαφορετικά νήματα με απρόβλεπτο τρόπο |
| **Coherence (Συνοχή)** | Το hardware εγγυάται μία έγκυρη τιμή ανά πάσα στιγμή |
| **Consistency (Συνέπεια)** | Δική μας ευθύνη: όλα τα νήματα να βλέπουν ίδια σειρά μεταβολών |
| **n = n+1 δεν είναι atomic** | Είναι load + increment + store — 3 βήματα, μπορεί να διακοπεί ανάμεσα |
| **Αμοιβαίος αποκλεισμός** | Μόνο 1 νήμα τη φορά μπαίνει στο κρίσιμο τμήμα |
| **Στόχος** | Ελαχιστοποίηση μεγέθους κρίσιμου τμήματος — μόνο το απαραίτητο κλειδώνεται |
| **Lock / Mutex** | lock()/unlock(), αναστολή (όχι busy wait) σε αποτυχία, λειτουργεί και σαν memory fence |
| **try/finally με lock** | Εγγυάται unlock ακόμα και σε exception/early return |
| **Semaphore (binary)** | acquire()/release() — like lock, αλλά με εσωτερική ουρά, ο επόμενος μπαίνει κατευθείαν |
| **Fair vs weak lock/semaphore** | Fair = FIFO σειρά· weak = τυχαία σειρά (αλλά όχι starvation) |
| **volatile** | Λύνει μόνο visibility, ΟΧΙ atomicity/ordering — δεν αρκεί μόνο του |
| **synchronized** | Ενσωματωμένο στη Java· σημαίνει αμοιβαίο αποκλεισμό (όχι "συγχρονισμό" σειράς)· κλειδώνει συγκεκριμένο αντικείμενο |
| **Κλειδώνουμε μεταβλητή, όχι ενέργεια** | Όλες οι πράξεις πάνω στην ίδια μεταβλητή πρέπει να μοιράζονται το ίδιο lock |
| **Barrier** | Συγχρονισμός σημείου συνάντησης (όχι αμοιβαίος αποκλεισμός) — θα καλυφθεί αργότερα |
| **Signaling / semaphores γενικά** | Καθορίζει ΠΟΙΟΣ μπαίνει πρώτος, όχι μόνο ότι μπαίνει ένας — θα καλυφθεί αργότερα |
